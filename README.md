# danta — 주식 단타 자동매매 프로젝트

이 저장소는 **코드 원본·검증 후보·인수인계·자동검증 보고서·장별 실행 결과**를 분리해서 관리합니다.

## 폴더 구조

- `CURRENT.md` — 현재 검증 기준본과 다음 작업
- `code/releases/` — **최종/기준 `.ipynb` 코드를 바로 보관**
- `code/candidates/` — 비교·독립검증용 후보 코드
- `handoff/` — 날짜별 인수인계서
- `reports/build/` — 빌드 검증 보고서
- `reports/comparison/` — 코드 비교 보고서
- `reports/regression/` — 회귀테스트 결과
- `reports/inspection/` — 핵심 구현 점검 보고서
- `reports/analysis/` — 장별 실행 결과 분석
- `reports/design/` — 다음 버전 수정·복구 설계
- `DATA_ANALYSIS_GUIDE.md` — 재사용 가능한 실행 결과 분석 지침
- `data/` — `버전(실행일자)` 형식의 장별 실행 결과
- `research/` — 장중 운영 코드와 분리한 독립 수집·백테스트 프로젝트
- `.github/` — 자동 빌드/비교/검증 도구와 workflow

## Release 규칙

`code/releases/`에 들어가면 버전 폴더를 다시 거치지 않고 `.ipynb` 파일을 바로 볼 수 있게 관리합니다.

파일명의 날짜는 **해당 코드를 실제로 실행할 예정인 날짜**를 기준으로 합니다.

예:

```text
code/releases/
├─ 013_260830_v1.6.7_startmsg_fix.ipynb
├─ 014_260902_v1.6.8.ipynb
└─ 015_260903_v1.6.9.ipynb
```

기본적으로 release에는 `.ipynb`만 보관합니다. `.txt`와 `.py` 복사본은 별도 요청이 있을 때만 만듭니다.\n\n독립 연구용 코드·노트북 파일명은 운영 release와 구분할 수 있도록 `RES_` 접두어를 사용합니다. 예: `RES_001_ETF_과거분봉_수집백테스트.ipynb`.

## 실행 결과 업로드 규칙

장 종료 후 생성된 CSV와 상태 JSON은 `data/` 아래에 **`버전(날짜)`** 폴더로 묶어 올립니다.

폴더명 형식은 `X.Y.Z(YYMMDD[, YYMMDD...])`입니다. 같은 버전으로 여러 날짜를 실행했다면 날짜를 쉼표로 구분해 한 폴더에 기록합니다.

예:

```text
data/
├─ 1.6.7(260831, 260901)/
│  ├─ scanner_signals_v167.csv
│  ├─ scanner_system_v167.csv
│  ├─ paper_entry_decisions_v167.csv
│  ├─ paper_entry_path_v167.csv
│  ├─ paper_post_exit_v167.csv
│  ├─ paper_trades_v167.csv
│  ├─ live_orders_v167.csv
│  ├─ live_trades_v167.csv
│  └─ live_state_v167.json
└─ 1.6.8(260902)/
   └─ ...
```

해당 날짜에 생성되지 않은 파일 종류는 억지로 만들 필요가 없습니다. 실행 결과 폴더는 저장소 루트가 아니라 항상 `data/` 아래에 둡니다.

최신 검증 코드 전체를 보존하고, 필요한 변경점만 최소 수정·통합한 뒤 새 전체본을 생성합니다.
프로젝트 채팅은 설계·결정·리뷰의 본체로 사용하고, GitHub 저장소는 완성된 코드·인수인계서·데이터 원본의 기본 보관 위치로 사용합니다.

## 프로젝트 불변 기준 (PROJECT CONTINUITY)

이 절은 버전별 기능보다 상위에 있는 장기 운영 원칙입니다. 향후 분석·설계·코드 작성 시 반드시 **README.md + 해당 작업의 최신 인수인계서 + 직전 검증 release 전체 코드**를 함께 읽습니다.

문서 역할은 다음과 같습니다.

- `README.md`: 모든 버전에 적용되는 불변 원칙
- 최신 인수인계서: 해당 분석·릴리스에서 합의한 구체적인 변경사항
- 직전 검증 release: 삭제하거나 재구성하지 않고 직접 승계할 구현 기준
- 새로운 명시적 사용자 결정이 있을 때만 기존 원칙을 변경하며, 변경 이유와 날짜를 README와 CONTINUITY에 기록

### 1. 분석과 코드 작성 단계 분리

기본 작업 순서는 다음과 같습니다.

1. 장 종료 결과와 과거 데이터를 병합·검증·분석
2. 확정·보류·기각 사항을 구분한 다음 릴리스용 인수인계서 작성
3. 새 채팅에서 인수인계서와 직전 검증 코드를 기준으로 전체 코드 작성
4. 부모 정의 보존·구문·cold-start·회귀검증 후 release 등록

데이터 분석과 전체 코드 작성을 한 번에 진행하지 않습니다. 표본이 부족하면 실전 조건을 완화하지 않고 Shadow 수집을 연장합니다.

### 2. Parent preservation

새 버전은 직전 최신 검증 코드를 처음부터 다시 쓰는 작업이 아닙니다.

- 사용자가 지정한 직전 검증 release를 직접 읽고 필요한 부분만 최소 수정·통합
- 기존 함수·클래스·상수·import·주문엔진·연구체계·파일 구조 보존
- QUICK REFERENCE와 PROJECT CONTINUITY는 부모 원문을 유지하고 append-only로 추가
- `if __name__ == "__main__": run_scanner()`는 프로그램 셀 최하단에 정확히 1회
- 일부 검색 결과나 과거 답변의 코드 조각으로 전체 코드를 재조립하지 않음
- parent definition preservation, top-level use-before-definition, compile, 외부 연결을 막은 cold-start, 행동 회귀검증 필수

### 2-1. 전체 코드 완료 조건: 2단계 검증과 비판적 재검토

전체 코드 작성은 최초 구현과 1차 테스트 통과만으로 완료 처리하지 않습니다. 사용자가 별도로 요청하지 않아도 다음 과정을 하나의 기본 작업으로 수행합니다.

1. 부모 코드에서 확정 변경사항만 최소 수정·통합
2. 전체 셀 compile, import·미정의 이름, 부모 정의 보존, 외부 연결 차단 cold-start와 mock 회귀시험
3. 최초 구현 관점에서 벗어난 독립적인 2차 비판적 코드 리뷰
4. 시간 산식·상태 전환·동시성 경합·중복주문·실패 및 복구·설정 배치·CSV와 알림 일치 여부 재점검
5. 2차 리뷰에서 발견된 문제 수정
6. 수정된 최종본에 전체 회귀시험을 처음부터 다시 실행
7. 최종본만 release 및 GitHub에 등록
8. 사용자가 **전체 코드 작성**을 요청한 경우, 위 검증이 모두 PASS하면 별도의 `main 업로드` 추가 요청이나 재확인을 기다리지 않고 같은 작업에서 최종 코드를 `code/releases/`에 저장하고 **main 브랜치에 바로 커밋**한다.
9. 검증 실패, 미해결 문서 충돌, 주문·데이터 안전 관련 미해결 위험이 있으면 main에 등록하지 않고 그 사유를 사용자에게 명확히 보고한다.

2차 리뷰에서는 단순히 같은 테스트를 반복하지 않고, 테스트가 놓친 경계상황과 구현·문서 간 불일치를 반대 관점에서 찾습니다. 최종 보고에는 `1차 구현 결과`, `2차 리뷰 발견사항`, `수정내용`, `최종 회귀검증`, `실제 broker에서 확인하지 못한 잔여위험`을 구분해 기록합니다.

검증 수준은 다음 세 단계로 구분하며 서로 같은 의미로 표현하지 않습니다.

- 정적·mock 검증 통과
- 소액 실전 확인 가능
- 실전 확대 가능

mock 검증 통과만으로 실전 무결함이나 실전 확대 가능을 선언하지 않습니다. 키움 서버 응답, 실제 체결 순서, 네트워크 단절 등 mock으로 확정할 수 없는 항목은 소액 실전 결과를 별도로 확인합니다.

### 3. 주문 안전장치 우선

과거 실전 사고를 막기 위한 다음 구조는 명시적 합의 없이 삭제·우회하지 않습니다.

- `requested_qty - unfilled_qty` 기반 체결수량 계산과 초과수량 invariant
- broker 실제 보유수량·매도가능수량·미체결 조회
- 자동관리수량과 외부/수동 보유수량 분리
- 중복 BUY/SELL 및 초과매도 방지
- `ORDER_STATUS_UNKNOWN` SAFE HALT와 `EXIT_ERROR`
- shutdown 이후 신규 주문 차단
- `live_state` atomic save·복구
- 주문·체결·사전조회 latency 및 slippage 기록
- 실제 주문의 API 처리 우선순위는 `손절 SELL > 기타 SELL > 위험축소 취소·정정 > 신규 BUY > 주문상태 확인 > 일반 조회·스캔`으로 유지
- 이미 전송 중인 HTTP는 강제 중단하지 않되, 시작 전인 낮은 우선순위 요청을 대기시켜 주문이 다음 API 슬롯을 획득하도록 구성
- 주문 우선처리도 증권사 전역 호출간격과 중복·수량 안전장치를 우회하지 않음

청산 지연 개선은 안전검사를 제거하는 방식이 아니라 독립 조회 병렬화, 단계별 시간계측, 실패 처리 강화 방식으로 검증합니다. 일부 조회만 성공한 상태를 정상 잔고로 간주하지 않습니다.

#### Import 및 실제 주문경로 검증 원칙

- 새 코드에서 사용하는 표준 라이브러리와 외부 패키지는 사용 지점만 추가하지 말고 import 목록·의존성·실행 가능 여부를 함께 점검
- `uuid`처럼 주문경로에서 사용하는 이름은 정적 미정의-name 검사, 전체 셀 compile, 외부 주문을 mock한 cold-start 및 실제 함수 호출 회귀테스트로 누락 여부 확인
- 함수 존재 여부나 정책 판정만 검사하지 않고 `가격 tick → TP/SL 판정 → submit_live_exit → cache 또는 REST 검증 → SELL 제출 → 주문번호 기록`의 end-to-end 경로를 실행
- import 또는 cache 처리 예외가 실제 SELL API 호출 전에 발생하면 캐시 경로를 폐기하고, broker 보유수량·매도가능수량·미체결을 새로 조회하는 기존 REST 청산 경로로 즉시 전환
- 매도경로 오류가 발생하면 신규 실제매수는 SAFE HALT하되 기존 보유종목의 가격감시·청산·체결확인은 계속 수행
- SELL API 호출 이후 timeout·연결단절·주문번호 누락처럼 주문 접수 여부가 불명확하면 중복매도하지 않고 broker 주문·체결·미체결 상태를 먼저 확인
- import 누락 또는 미정의 이름을 발견하지 못하는 회귀테스트는 통과로 간주하지 않음

#### 깨끗한 실행환경·시간경계 검증 원칙

2026-09-14 v2.1에서 테스트 프로세스가 먼저 import한 `copy` 때문에 release 자체의
import 누락이 가려졌고, `selected_exit_strategies` 미정의도 정상 반환까지 호출하지 않은
mock에서 누락됐다. 같은 유형을 막기 위해 다음 항목을 release 승인 조건으로 강제한다.

- 검증 스크립트의 전역 이름을 release에 주입하거나 같은 Python 프로세스의 오염된 namespace를 재사용하지 않음
- 모든 코드 셀을 합친 독립 소스에 `pyflakes` 미정의-name 검사를 실행하고, 허용 예외는 Jupyter 제공 이름처럼 근거가 명확한 이름만 검사 도구에 명시
- 별도 새 Python 프로세스와 깨끗한 namespace에서 cold-start를 수행하며 테스트용 선행 import로 누락을 보완하지 않음
- 함수 존재·중간 상태 등록만 확인하지 않고 신규·변경 함수가 예외 없이 끝까지 반환하는지 검증
- 함수 인자를 추가하거나 이름을 변경한 경우 선언, 실제 사용, 로그, CSV 저장, 호출부를 함께 추적하고 사용되지 않은 인자와 이전 이름 잔존을 실패 후보로 검토
- 09:00 전용 로직처럼 현재 시각 guard가 있는 경로는 장외 단순 실행으로 통과시키지 않고 가상시계와 고정 fixture로 시작 직전·시작·종료 직전·종료 직후를 모두 호출
- 가상시계로 최소 `08:59:50`, `09:00:05`, `09:01:00`, `09:05:00`, `09:15:00`, `09:15:01`, ETF 판단시각, 장 종료·flush 경계를 재생
- 장외 검증은 `RESEARCH`와 별도의 명시적 안전 플래그, 별도 출력경로, 실제·모의 broker 주문 0건 assertion을 사용하며 실장 데이터에 섞지 않음
- 정적검사에서 의도적으로 import 또는 지역변수 정의 하나를 제거한 negative-control이 실패하는지 확인한 뒤에만 검사기 자체를 신뢰
- 검증 결과와 사용 명령을 `reports/`에 남기지 않은 release는 검증 완료로 표시하거나 `CURRENT.md`의 실행 대상으로 올리지 않음

`python .github/tools/validate_release_notebook.py <release.ipynb>`가 실패하면 해당 release는
장중 실행 금지다. 정적검사 통과는 시간경계 replay와 행동 회귀검증을 대체하지 않는다.

#### 신규 주문 프로세스의 안정 경로 보존 원칙

- 매매 주문 프로세스를 개선할 때는 직전 검증 release의 안정적인 주문 방식을 삭제하지 않고, 새 경로와 분리된 fallback 경로로 같은 release 안에 보존
- fallback은 과거 `.ipynb`나 이전 버전 프로그램을 런타임에 다시 실행하는 방식이 아니라, 현재 상태모델·중복방지 원장과 호환되는 명시적 함수로 구현
- 신규 **매도** 경로가 SELL API 호출 전에 예외·검증실패·의존성 오류를 내면 신규매수를 SAFE HALT하고, 직전 검증 방식으로 broker 보유수량·매도가능수량·미체결을 재조회한 뒤 확인된 자동관리수량의 청산을 계속
- 신규 **매수** 경로가 실패하면 이전 방식으로 매수를 강행하지 않고 해당 신규매수를 취소·차단. 보유하지 않은 위험을 새로 만들 필요가 없으므로 매수에는 fail-closed 원칙 적용
- 주문 API 호출 이후 접수 여부가 불명확한 오류에는 fallback 재주문을 금지하고, broker 주문·체결·미체결·보유수량을 먼저 대조
- fallback 경로도 독립 end-to-end 회귀테스트를 통과해야 하며, 새 경로와 같은 미검증 helper·executor·의존성에 묶어 두 경로가 동시에 실패하지 않도록 구성
- fallback 전환 사실, 원인, 원래 경로, 사용한 안정 경로, 조회수량, 주문번호와 최종 체결상태를 주문 원장과 긴급 알림에 기록
- 새 주문 경로와 안정 경로가 상태·수량·중복방지 측면에서 함께 검증되지 않으면 실제매매 release로 승인하지 않음

### 4. 연구와 실제매매 분리

- 연구 후보는 먼저 Shadow/counterfactual로 수집
- 충분한 날짜 밖 검증 없이 실제 주문에 연결하지 않음
- 기존 BASE, PRE_HISTORY, FIRST_75_PASS, LATER_PASS, CONFIRM, LIVE_FILTER_SHADOW, SHADOW_SCORE_70_74, WIDE_HIGH_GAP_SHADOW, PRE_FAIL_PULLBACK_SHADOW, WATCH Episode, ENTRY_PATH, POST_EXIT, 169개 TP/SL grid 보존

- 새 전략의 실전 승격 여부는 표본 수, 날짜별 재현성, 비용 후 기대값과 Profit Factor로 결정

- 향후 예약 모드는 `"MOCK"`, `"LIVE"`이며 사용자 명시적 결정 없이 기본값을 변경하지 않는다.

### 5. 데이터 병합·성과 분석 원칙

- `paper_trades`의 TP 13 × SL 13 = 169행은 169개 독립 거래가 아니라 하나의 `trade_id`에 대한 169개 전략 결과
- 진입 표본은 고유 `trade_id`, 전략 결과는 `trade_id + TP + SL` 단위로 구분
- 원본 대용량 CSV와 분할본을 동시에 중복 적재하지 않음
- 분할본은 part 순서, 반복 헤더 제거, UTF-8 BOM 처리 후 논리적으로 결합
- 버전별 컬럼 합집합과 provenance를 보존하고 없는 값은 임의 추정하지 않음
- `stock_code`는 문자열로 보존
- 진입 시점 이후의 MFE·MAE·청산 결과를 진입 feature로 사용하는 미래정보 누수 금지
- 날짜 순서 기반 holdout/walk-forward 및 동일 종목·동일 날짜 그룹 분리
- 모든 성과는 gross와 net을 함께 표시한다. 과거 결과는 당시 기준 0.23%를 유지하고,
  **v1.7.0 이후 신규 연구·보고는 왕복 추정비용 0.24%**를 기본값으로 사용한다.
- 승률뿐 아니라 표본 수, 평균·중앙값, gross/net Profit Factor, MFE/MAE, 손실 꼬리, 날짜별 안정성을 함께 평가

#### Telegram 메시지 가독성 규칙

모든 신규·기존 전략의 Telegram 진입·주문·체결 알림은 다음 형식을 공통으로 적용합니다.

- 첫 줄에는 이모지, 전략명, 이벤트 종류를 짧게 표시한다.
- 종목명 다음 줄에 `종목코드 : 000000`을 단독으로 표시하고 그 뒤에는 빈 줄을 둔다.
- 시간·가격·진입근거·전략처럼 같은 성격의 항목은 같은 문단으로 묶고, 서로 다른 문단 사이에만 빈 줄을 둔다.
- 문단 제목은 `⏱ 진입`, `💰 가격`, `📊 차트판정`, `🎯 전략`처럼 짧게 쓰고, 세부 항목에는 `-` 글머리기호를 사용한다.
- 모든 항목 사이에 빈 줄을 넣거나 모든 줄에 같은 글머리기호를 반복하여 메시지를 불필요하게 길게 만들지 않는다.
- 공통정보를 반복해서 붙이지 않고 해당 전략의 진입판정에 필요한 핵심 근거만 표시한다.
- 신호시각과 체결시각, 신호가와 체결가는 서로 다른 값이므로 각각 별도 줄에 표시한다.
- 연구용 진입은 메시지 마지막에 `연구용 가상진입`과 `실제주문 없음`을 각각 명시한다.
- SNAPSHOT은 평가만으로 알림을 보내지 않고 실제 가상진입 생성 시에만 발송하며, 제목에 `20분`, `40분`처럼 평가 horizon을 표시한다.
- TP/SL·가격·점수·시간·전략명은 실제 runtime 값에서 동적으로 만들며 표시용 문자열로 하드코딩하지 않는다.

1. 먼저 두 문서의 차이가 진짜 충돌인지, `장기 원칙`과 `이번 버전 기본값`의 역할 차이인지 구분한다.

3. 단, 부모 보존·주문 안전장치·실주문 연결·데이터 무결성처럼 장기 안전원칙과 충돌하거나 해석이 둘 이상이면 임의 적용하지 않는다.
4. 안전·실주문·데이터 보존 관련 미해결 충돌이 하나라도 있으면 전체 코드 작성을 중단하고 사용자에게 선택지를 제시해 확인받는다.
5. 사용자가 결정하면 코드, 최신 인수인계서, README의 관련 문구를 같은 작업에서 함께 정리하고 CONTINUITY에 근거와 날짜를 남긴다.
6. 불분명한 새 전략·필터·청산정책은 실제 주문에 연결하지 않는다. 합의 전에는 Shadow 또는 미구현 상태로 둔다.
