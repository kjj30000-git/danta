# v2.2.0 독립 2차 비판적 검토

## 발견하고 수정한 항목

1. SUPPORT 진입 뒤 같은 완료봉에서 새 고점과 지지 이탈이 함께 관찰될 때 상태 전이가 모호했다. 이미 진입한 후보도 지지 붕괴를 평가하도록 수정했다.
2. 프로그램 재시작 뒤 첫 새 분봉이 이전 분봉과 연속인 것처럼 처리될 여지가 있었다. 복구 후 첫 분봉을 명시적으로 불완전 처리했다.
3. WebSocket 재접속은 기존 local sequence가 연속이어도 실제 데이터 공백일 수 있었다. 재접속 시 sequence gap을 강제로 만들어 해당 분봉의 지지 시간을 인정하지 않도록 수정했다.
4. 상태 checkpoint 직전 `FILL` 원장만 저장된 충돌창에서 재시작하면 중복진입 위험이 있었다. 신호 CSV의 `FILL`을 대조해 종목·전략 일간 중복키를 복구하도록 보완했다.
5. 후보 등록과 구독 해제의 순서 경합을 manager lock에서 재확인하도록 수정했다.
6. 신호 원장의 event id가 같은 episode의 여러 신호를 구분하지 못할 수 있었다. signal time을 키에 추가했다.
7. 후보 수, 열린 전략 수, tick/writer backlog, 분봉 무효화와 알림 상태를 별도 metric으로 기록했다.

## 반대 관점 검증

- `scan_market()` 전체 mock 실행에서 BASE와 FIRST_75만 생성되고 반복 scan에서 중복 grid가 생기지 않음
- PRE 조건 실패 종목이 FIRST_75 알림·후보에 포함되지 않음
- state 저장 실패 시 마지막 정상 파일을 보존하고 신규 연구진입만 중단하며 열린 grid 청산은 계속됨
- Telegram 발송 결과 불명확 및 전송 중 프로세스 종료는 `DELIVERY_UNKNOWN`으로 보존되고 자동 재전송되지 않음
- 연구 lock을 점유한 상태에서도 WebSocket callback이 기다리지 않음
- 실제 연구 worker가 확장 tick tuple을 처리하고 queue-full 시 최신 snapshot을 volume/sequence와 함께 coalescing함
- 08:00 이전 사용자 중단과 20:00 종료에서 shutdown gate, flush, executor 종료가 수행됨
- 부모 실제청산 E2E mock의 FAST CACHE, SAFE REST fallback, 주문상태 불명확 처리가 회귀 유지됨

결과: **32/32 PASS**, 외부 연결 0건, 실제·모의주문 0건.

## 장중에서 확인할 잔여위험

- Kiwoom 0B의 필드 `15`가 실제 환경에서 누적거래량인지 체결량인지 최종 확인해야 한다. 값이 없거나 신뢰할 수 없으면 volume feature는 `N/A`이며 진입 필터로 쓰지 않는다.
- queue sequence gap은 프로세스 내부 drop과 재접속을 감지하지만, 서버가 조용히 누락한 tick까지 증명하지는 못한다.
- 종료·재시작 중 Telegram 수신 여부가 불명확하면 중복 방지를 우선해 자동 재전송하지 않는다.
- 장중 첫날에는 `pullback_metrics_v220.csv`의 backlog, invalid bar, save failure와 Telegram 도착 여부를 확인해야 한다.
