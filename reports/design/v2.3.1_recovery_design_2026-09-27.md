## 2. 확인된 결함

### 2.1 모든 완료봉 무효화

`v220_on_tick()`은 매 tick마다 `v230_init_candidate()`를 호출한다. 초기화 함수의 defaults에 `next_bar_partial=True`가 들어 있어 새 봉 생성 시 `pop()`으로 소비한 플래그가 같은 분의 다음 tick에서 다시 생성된다. 다음 분봉 생성 때마다 해당 플래그가 소비되어 모든 봉이 `valid=False`가 됐다.

실행 결과는 완료봉 9,526개, 무효봉 9,526개이며 후보 17개 모두 `high=null`, `L1=null`, `history=0`이다.

### 2.2 후보별 1분봉 원장 누락

v2.3.0이 `v220_complete_bar()`를 덮어쓰면서 v2.2.0에 있던 `pullback_candidate_1m_*.csv` 저장 블록을 포함하지 않았다. 따라서 사용자가 생성된 파일을 모두 업로드했어도 후보별 OHLC를 이용한 사후 재평가가 불가능했다.

### 2.3 검증 공백

기존 v2.3.0 fixture는 `valid=True`인 완성봉을 직접 `v220_complete_bar()`에 전달했다. 실제 실행 경로인 동일 분 내 복수 tick, 후보 생성 중간봉, 분 전환, 재접속·sequence gap을 통과하지 않아 플래그 재생성 오류를 발견하지 못했다.

## 3. 상태관리 수정

### 3.1 초기 생성과 스키마 보완 분리

현재 `v230_init_candidate()`의 역할을 두 함수로 분리한다.

1. `v230_create_candidate_state()`
   - 신규 후보 생성 때 한 번만 호출
   - `needs_partial_bar=True` 설정
   - H/L1/R1/B/L2, history, pending 등 신규 상태 생성

2. `v230_ensure_candidate_schema()`
   - 복구한 구버전 상태의 누락 필드만 보완
   - 매 tick 호출 가능하도록 멱등성 보장
   - 소비되는 일회성 플래그를 다시 `True`로 만들지 않음

### 3.2 부분봉 플래그 소비

`pop()`으로 키를 지우지 않고 값만 전환한다.

```python
partial = bool(c.get("needs_partial_bar", False))
partial = partial or minute <= candidate_start_minute
c["needs_partial_bar"] = False
```

- 신규 후보: 등록된 현재 분만 부분봉
- 다음 완전한 분부터 유효봉
- 동일 분의 추가 tick: 플래그를 되살리지 않음
- 당일 복구·WebSocket 재접속: 명시적으로 `needs_partial_bar=True` 설정
- 일반 스키마 보완: 현재 값을 변경하지 않음

### 3.3 공백 후 회복

무효 원인을 상태에 명시한다.

- `INITIAL_PARTIAL`
- `CANDIDATE_START_PARTIAL`
- `SEQUENCE_GAP`
- `NON_CONTIGUOUS_MINUTE`
- `POST_RECONNECT_PARTIAL`
- `WRITE_UNAVAILABLE`

공백이 발생한 봉만 무효화하고, 다음 연속 완료봉부터 history를 다시 쌓는다. 무효봉을 지지·돌파·SNAPSHOT 판정에 사용하지 않는다.

## 6. 검증 설계

### 6.1 실제 tick→분봉 회귀검증

완성봉을 직접 주입하는 검증만으로 승인하지 않는다. `handle_realtime_price`와 동일한 입력 형태에서 `v220_on_tick`까지 실행한다.

필수 fixture:

1. 후보 생성 중간 분에 복수 tick
   - 최초 부분봉 1개만 무효
   - 다음 2개 이상의 분봉은 유효
   - `bars > invalid_bars`, history 증가, high 생성

2. 같은 분 복수 tick
   - 플래그가 다시 생성되지 않음
   - OHLC와 tick_count 정확

3. 분당 tick 1개
   - 연속 분이면 유효봉 생성

4. 한 분 무수신
   - 다음 봉 `NON_CONTIGUOUS_MINUTE`
   - 이후 연속봉에서 자동 회복

5. sequence gap
   - 해당 봉만 무효
   - 다음 정상봉부터 회복

6. WebSocket 재접속
   - 재접속 경계 봉을 구조 판단에서 제외
   - 이후 유효봉 재개

7. 재시작 상태 복구
   - 과거 pending 취소
   - 부분봉 1회만 제외
   - 일간 중복키 유지

## 10. 추가 코드 감사에서 확인한 필수 수정

### 10.1 SNAPSHOT 저장 성공 전 상태 확정 금지

현재 `v230_snapshot()`은 `enqueue_research_rows()`의 반환값을 확인하지 않고 `snapshots_done`을 기록하며, READY이면 신규 신호까지 만들 수 있다. 원장 저장이 실패했는데 진입은 생성되는 불일치가 생길 수 있다.

v2.3.1에서는 다음 순서를 강제한다.

1. SNAPSHOT row P1 저장 또는 복구 spool 성공
2. 저장 성공 확인
3. `snapshot_results`, `snapshots_done`, `snapshot_ready` 갱신
4. DIRECT signal 생성

저장이 실패하면 해당 신규전략을 health halt하고 SIGNAL/FILL을 만들지 않는다.

### 10.2 모든 출력 파일 v2.3.1 분리

pullback 파일만 바꾸지 않고 실행 중 생성되는 모든 결과 파일명을 점검해 `v231`로 분리한다. v2.3.0 결과에 이어쓰기하지 않는다.

- scanner signals/system
- paper trades/decisions/path/policy/post-exit
- pullback state/minute/signals/snapshot/metrics
- 기존 ETF 파일은 스키마가 바뀌지 않더라도 provenance에 실행 버전과 날짜를 보존하고 혼합 여부를 검증

시작 검증에서 active output path 목록을 출력하고 `v230` 잔존 경로가 있으면 실패시킨다. 의도적으로 유지하는 호환 파일은 허용목록과 이유를 명시한다.

### 10.3 손상 상태와 신규 상태 분리

v2.3.0의 후보 상태는 모든 history가 비어 있어 v2.3.1로 복원하면 안 된다.

- 신규 상태 파일 `pullback_state_v231.json` 사용
- state schema를 올리고 `schema`, `strategy_version`, `trading_date`를 검증
- v2.3.0 state 자동 승계 금지
- 같은 날 v2.3.1 재시작만 v2.3.1 state에서 복구
- 호환되지 않는 state는 원본을 보존하고 명확한 오류로 시작 중단

### 10.4 일자 전환 시 누적 계측 초기화

`v220_reset_day()`에서 후보와 신호뿐 아니라 다음도 함께 초기화한다.

### 10.6 활성 함수 정의 감사

부모 호환을 위해 `v220_complete_bar`, `v220_on_tick`, `v220_restore`, `validate_v220_config` 등이 여러 번 정의되어 있다. Python에서는 마지막 정의만 실행되므로 수정 위치가 잘못되면 테스트 코드와 장중 코드가 다른 구현을 사용할 수 있다.

이번 복구에서는 대규모 재구성을 하지 않되 다음을 검증한다.

- 실제 활성 함수의 source line과 코드 hash 기록
- 호출부가 기대한 마지막 정의를 가리키는지 assertion
- 부모 호환 함수와 v2.3.1 활성 함수의 역할을 주석으로 명확히 표시
- 회귀보고서에 활성 정의 목록 첨부

### 10.7 metrics 의미 보강

기존 `bars`와 `invalid_bars` 외에 다음을 추가한다.

- `valid_bars`
- `initial_partial_bars`
- `candidate_start_partial_bars`
- `sequence_gap_bars`
- `non_contiguous_bars`
- `post_reconnect_partial_bars`
- `minute_write_failures`
- `snapshot_write_failures`
- `candidates_with_valid_bar`
- `candidates_with_high`
- `candidates_with_l1`

항상 `bars == valid_bars + invalid_bars`가 성립해야 하며, reason별 무효봉 합도 `invalid_bars`와 일치해야 한다.

### 10.8 장중 조기 이상 알림과 종료 요약 분리

장중 health gate 실패는 즉시 1회 알림을 보내고 신규 세 전략을 중단한다. 종료 시에는 별도 요약으로 다음을 보낸다.
