# 자동매매 릴리스 2차 검증 기준

## 1. 목적

2차 검증은 1차 구현과 자체 테스트를 단순 반복하는 절차가 아니다. 최종 릴리스 후보를 독립적으로 다시 읽고, 정상 경로 밖의 경계 조건·복구 경로·검사기 자체의 누락 가능성을 찾아 실제 장애가 장중 실행이나 주문으로 이어지기 전에 차단한다.

2차 검증의 최종 판정은 다음 세 조건을 모두 만족해야 `PASS`로 한다.

1. 릴리스 코드가 깨끗한 환경에서 시작할 수 있다.
2. 기존 동작을 보존하면서 이번 변경사항이 명세대로 작동한다.
3. 일부 저장·통신·데이터가 실패해도 잘못된 판단이나 주문으로 진행하지 않는다.

## 2. import 및 미정의 이름 검사

import 누락과 미정의 변수는 반드시 2차 검증 범위에 포함한다. 특히 과거 `copy`, `uuid`, `selected_exit_strategies` 누락처럼 테스트 프로세스의 선행 import나 호출되지 않은 분기에 의해 가려지는 문제를 방지한다.

### 필수 검사

- 모든 코드 셀을 각각 `compile()`하여 문법 오류와 셀 단위 컴파일 실패를 확인한다.
- 모든 코드 셀을 실행 순서대로 합친 독립 소스에 `pyflakes`를 실행하여 `undefined name`을 확인한다.
- 테스트 프로세스가 미리 import한 이름을 릴리스 namespace에 섞지 않는다.
- 새 Python 프로세스와 깨끗한 namespace에서 시작 경로를 실행한다.
- 실제 기본 설정으로 `run_scanner()` 시작 경로를 토큰 요청 직전까지 실행한다.
- Jupyter가 제공하는 `display`, `get_ipython`만 근거가 명확한 허용 예외로 관리한다.
- 의도적으로 import 또는 변수 정의를 제거한 임시 사본이 검사에서 실패하는지 negative control로 확인한다.

`compile()` 성공만으로는 import 누락이나 미정의 이름을 검출할 수 없다. 반대로 `pyflakes` 정적검사만으로는 동적 분기 안의 외부 패키지 설치 여부나 실제 호출 시점 오류를 모두 보장할 수 없다. 따라서 정적검사와 clean-process 실행을 함께 통과해야 한다.

### v2.3.1 확인 결과

- 전체 셀 결합 후 pyflakes 미정의 이름: `PASS`

## 3. 2차 검증의 주요 작업

| 구분 | 검증 내용 | 실패 시 판정 |
|---|---|---|
| 코드 완전성 | 셀별 compile, import, 미정의 이름, 의존성 확인 | 릴리스 중단 |
| 깨끗한 시작 | 선행 import·기존 전역값 없는 새 프로세스에서 실행 | 릴리스 중단 |
| 기존 코드 보존 | 부모 버전 함수·클래스·상수 수량과 AST 비교 | 의도하지 않은 차이는 중단 |
| 핵심 주문경로 | 주문·broker 핵심 정의 변경 여부, 외부 주문 차단 | 불명확한 변경은 중단 |
| 변경 기능 | 실제 tick/fixture로 신규 기능과 산출물 검증 | 명세 불일치는 중단 |
| 경계 조건 | 분 전환, sequence gap, WebSocket 재접속, 날짜 변경 | 이중 처리·누락 시 중단 |
| 장애 복구 | API 일부 실패, 저장 실패, CSV 점유, 스키마 충돌 | fail-closed가 아니면 중단 |
| 원자적 저장 | 임시 파일 작성 후 replace, 실패 시 기존 파일 보존 | 기존 파일 훼손 시 중단 |
| 종료 처리 | 종료 원장 생성, outbox flush, 중복 실행 안전성 | 누락·중복 시 중단 |
| 검사기 검증 | 결함을 재주입한 negative control이 실제 실패 | 검사기 신뢰 불가로 중단 |
| 안전성 | 외부 연결 수와 실제·모의 BUY/SELL 수 확인 | 1건이라도 발생하면 중단 |

## 4. 정상 경로보다 우선해서 보는 경계 조건

2차 검증에서는 정상 입력 1회 성공보다 상태 전환 전후를 집중적으로 본다.

- 첫 tick, 첫 유효 봉, 데이터가 전혀 없는 경우
- 분봉 마감과 sequence gap이 동시에 발생하는 경우
- WebSocket 재접속이 분 전환과 겹치는 경우
- 기존 진행 중 봉이 있는 경우와 없는 경우
- 부분봉·무효봉 다음의 정상 봉이 다시 유효해지는지
- 장 시작 전, 장 종료 후, 날짜가 바뀌는 순간
- API가 전부 실패하는 경우와 일부만 성공하는 경우
- CSV가 Excel 등에 점유되어 교체할 수 없는 경우
- 종료 함수가 반복 호출되어도 중복 저장·중복 알림이 없는지

v2.3.1에서는 이 단계에서 sequence gap·재접속과 분 전환이 겹칠 때 두 봉이 무효화되던 결함을 발견했다. 기존 경계 봉이 있으면 그 봉 하나만 무효화하고 다음 신규 봉은 정상 수집하도록 수정했으며, gap/reconnect 각각 정확히 1개 무효봉 뒤 회복하는 assertion을 추가했다.

## 5. 회귀검증과 보존 확인

- 부모 버전의 top-level 정의가 빠지지 않았는지 이름과 개수로 비교한다.
- 주문·체결·broker 핵심 함수는 AST를 비교하여 의도하지 않은 수정이 없는지 확인한다.
- 스캐너와 수익률 수집 셀을 각각 독립 fixture로 실행한다.
- 생성 CSV의 필수 열, 자료형, 행 병합, 부분매도 집계, 손익·수익률 계산을 확인한다.
- 자동/수동 분류는 추정하지 않고 확인 가능한 주문번호 근거만 사용한다.
- 불확정 값은 임의 생성하지 않고 빈값 또는 `UNKNOWN`으로 남긴다.

## 6. Negative control

최종본이 통과하는 것만으로는 검사기가 실제 결함을 잡는지 알 수 없다. 최종본의 임시 사본에 결함을 하나씩 재주입하고 각 검사가 반드시 실패해야 한다.

v2.3.1에서는 다음 4종을 확인했다.

1. 스키마 보완 시 부분봉 플래그 재활성화
2. minute 원장 저장 제거
3. SNAPSHOT 저장 실패 뒤 상태 진행
4. 수익률 셀에 주문 API `kt10000` 삽입

향후 import·미정의 이름 검증 변경 시에는 import 또는 지역변수 정의를 제거한 negative control도 반드시 포함한다.

## 7. PASS의 의미와 한계

2차 검증 `PASS`는 정적검사와 외부 연결을 차단한 회귀 환경에서 코드 결함을 발견하지 못했다는 뜻이다. 실제 키움 서버의 응답 지연, 실시간 데이터 품질, 장중 체결과 같은 운영 환경을 완전히 증명하지는 않는다.

따라서 첫 장중 실행의 최초 5분에는 다음을 별도로 확인한다.

- `valid_bars > 0`
- `invalid_bars < bars`
- 고가 등 핵심 값이 `null`이 아님
- 후보 종목의 minute 행이 생성됨
- health halt가 발생하지 않음
- 외부 주문이 허용된 모드라면 주문 전 설정과 예산을 다시 확인
