## 2. v2.3.0 실행에서 확정된 사실

사용자는 실행 시 생성된 결과 파일을 모두 제공했다. 신규전략 핵심 파일이 없었던 것은 사용자 업로드 누락이 아니라 코드 실행·저장 경로의 문제다.

### 2.1 신규전략 평가 실패

- 관찰 후보: 17종목
- 신규 STRUCTURE/SNAPSHOT SIGNAL: 0건
- 신규 paper FILL: 0건
- 완료봉: 9,526개
- 무효봉: 9,526개
- 유효봉: 0개
- 후보 17개 모두 `high=null`, `L1=null`, `history=0`
- 후보 17개 모두 종료 상태 `DATA_UNAVAILABLE`

시장에 조건 충족 종목이 없었다고 볼 수 없다. 모든 완료봉이 구조 조건 계산 전에 무효 처리되어 신규전략이 정상 평가되지 않았다.

### 2.2 직접 원인

`v220_on_tick()`이 매 tick마다 `v230_init_candidate()`를 호출하고, 초기화 defaults가 소비된 `next_bar_partial=True`를 다시 생성했다.

새 분봉을 만들 때 해당 플래그를 `pop()`해도 같은 분의 다음 tick에서 다시 생겼고, 다음 분봉이 계속 `valid=False`가 됐다. `v220_complete_bar()`는 무효봉이면 history를 비우고 H/L1/구조/SNAPSHOT 계산 전 반환했다.

### 2.3 후보별 1분봉 원장 누락

v2.3.0에서 `v220_complete_bar()`를 덮어쓰면서 부모 v2.2.0에 있던 `pullback_candidate_1m` 저장 블록을 포함하지 않았다. 사용자가 모든 생성 파일을 제공했어도 후보별 가격 경로를 사후 재구성할 수 없었다.

### 2.4 검증 공백

v2.3.0 신규 fixture는 `valid=True`인 완성봉을 `v220_complete_bar()`에 직접 주입했다. 실제 `tick → 동일 분 복수 tick → 분 전환 → 완료봉` 경로를 통과하지 않아 플래그 재생성 결함을 발견하지 못했다.

### 2.5 추가 확인된 위험

- `v230_snapshot()`은 P1 원장 enqueue 결과를 확인하지 않고 SNAPSHOT 완료·READY·SIGNAL로 진행할 수 있음
- output/state 파일을 새 버전과 분리하지 않으면 v2.3.0 결과와 혼합 가능
- v2.3.0 손상 state를 v2.3.1이 복원하면 빈 history 상태가 승계됨
- 버전 exact assertion 잔존 시 시작 단계 재차단 가능
- `v220_*` 핵심 함수가 여러 번 정의되어 실제 활성 정의와 수정 대상이 달라질 위험
- 일자 전환 시 일부 counters·sequence·health 상태가 이어질 가능성

## 5. 후보 상태관리 수정

### 5.1 생성과 스키마 보완 분리

`v230_init_candidate()` 역할을 분리한다.

- 신규 후보 생성 함수: 상태를 한 번 생성하고 `needs_partial_bar=True` 설정
- 스키마 보완 함수: 구버전 state의 누락 필드만 보완하며 일회성 플래그를 다시 활성화하지 않음

스키마 보완 함수는 매 tick 호출되어도 후보의 관찰 상태를 변경하지 않아야 한다.

### 5.2 부분봉 플래그

키를 `pop()`해 없애지 않고 Boolean 값으로 소비한다.

```python
partial = bool(c.get("needs_partial_bar", False))
partial = partial or minute <= candidate_start_minute
c["needs_partial_bar"] = False
```

- 후보 등록 현재 분: 부분봉
- 다음 완전한 분부터: 유효봉
- 같은 분 추가 tick: 플래그 재생성 금지
- 재시작·재접속: 명시적으로 1회만 부분봉 처리

### 5.3 무효 사유

각 무효봉에 다음 중 하나를 기록한다.

- `INITIAL_PARTIAL`
- `CANDIDATE_START_PARTIAL`
- `SEQUENCE_GAP`
- `NON_CONTIGUOUS_MINUTE`
- `POST_RECONNECT_PARTIAL`
- `WRITE_UNAVAILABLE`

무효봉은 구조 판단에 사용하지 않는다. 다음 정상 연속봉부터 history를 다시 쌓는다.

## 9. health gate와 종료 요약

후보 등록 후 5분 또는 완료봉 3개 시점에 검사한다.

- `bars > 0`
- `valid_bars > 0`
- `invalid_bars < bars`
- 유효봉 후보의 `high is not None`
- minute 원장 write 성공
- `bars == valid_bars + invalid_bars`
- 무효 사유별 합계가 invalid_bars와 일치

실패 시:

1. STRUCTURE/SNAPSHOT 신규 신호만 중단
2. BASE/FIRST_75와 기존 포지션 추적·청산 유지
3. counts·종목·무효 사유·최초시각을 로그와 Telegram으로 1회 알림
4. 반복 동일 알림 억제
5. 종료 요약에 health halt 기록

종료 요약에는 다음 funnel을 전략별로 표시한다.

```text
후보 → 유효봉 → H → L1 → STRUCTURE_READY
      → SNAPSHOT_READY → SIGNAL → FILL → 알림
```

### 11.2 조회자료

### 11.4 종목별 집계

동일 종목의 분할매수·부분체결·부분매도·여러 차례 매수매도를 거래일 단위 한 행으로 합친다.

```text
평균매입가 = 총 매입 체결금액 / 총 매입수량
평균매도가 = 총 매도 체결금액 / 총 매도수량
순수익금 = 실현매도금액 - 실현원가 - 매수수수료 - 매도수수료 - 세금
순수익률 = 순수익금 / 실현원가 × 100
```

- 일부만 매도하면 매도된 수량의 실현손익만 기록
- 잔여수량 별도 표시
- 전일부터 보유한 종목의 당일 매도는 broker 원가 사용
- 동일 종목 여러 차례 왕복매매도 일일 합계 한 행
- broker 비용 후 실현손익을 주 기준으로 보존
- 비용 분리값이 없으면 임의 추정하지 않음
- 자체 계산과 broker 값 불일치 시 `RECONCILIATION_REQUIRED`

필수 컬럼:

- trade_date, stock_code, stock_name
- buy_order_count, buy_fill_count, buy_qty, avg_buy_price, buy_amount
- sell_order_count, sell_fill_count, sell_qty, avg_sell_price, sell_amount
- realized_qty, broker_cost_basis
- gross_profit, buy_commission, sell_commission, tax, total_cost
- net_profit, net_return_pct
- broker_reported_profit, broker_reported_return_pct
- remaining_qty, position_status
- first_buy_time, last_sell_time
- classification, matched_auto_order_count, unmatched_order_count
- reconciliation_status, queried_at, collector_version

계좌번호·앱키·토큰은 저장하지 않는다.

### 11.5 자동·수동 분류

체결 주문번호를 당일 `live_orders_v231.csv`와 대조한다.

- 모두 일치: `AUTO_CONFIRMED`
- 일치·미일치 혼합: `MIXED`
- 모두 미일치: `MANUAL_OR_UNMATCHED`
- 자료 불완전: `UNKNOWN`

미일치 주문을 확정 수동매매로 표현하지 않는다. 자동 주문번호가 저장되기 전 프로그램 종료 또는 다른 자동 프로그램의 가능성을 보존한다.

### 11.6 실행 출력

```text
조회일: YYYY-MM-DD
거래 종목: N개
매수 총액: N원
매도 총액: N원
순수익금: N원
비용 후 수익률: N%
AUTO_CONFIRMED: N종목
MIXED: N종목
MANUAL_OR_UNMATCHED: N종목

```

조회 성공 0종목과 조회 실패를 구분한다. 실패 시 기존 누적 CSV를 덮어쓰지 않는다.
