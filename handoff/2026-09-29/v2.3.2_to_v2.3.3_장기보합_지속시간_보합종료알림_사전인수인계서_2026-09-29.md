## 1. 목적

v2.3.2 장기 보합 돌파 연구는 그대로 유지하되, 30분 누적 Telegram에서 최초 `60분 보합완성` 문구만 계속 반복되는 문제를 개선한다.

사용자가 다음 코드에서 원하는 핵심은 다음 두 가지다.

1. 살아 있는 보합 박스는 **Telegram 발송 시점 기준 현재 몇 분째 보합인지 계속 갱신**한다.
2. 보합이 깨진 종목은 누적 목록에서 사라지게 하지 않고 **보합종료 시각·총 지속시간·종료 사유**를 남긴다.

이번 사전 인수인계의 범위는 **장기 보합 Telegram 표현과 이를 위한 최소 상태/원장 보강**이다. 장기 보합의 진입 조건, 박스 상·하단, 돌파 판정, grid, 실제·모의 주문 정책은 변경하지 않는다.

## 2. 반드시 보존할 v2.3.2 동작

### 2.1 후보 등록과 완료봉

- 장기 보합 연구 대상은 v2.3.2와 동일하게 BASE 또는 FIRST_75_PASS로 등록된 후보를 사용한다.
- 후보 등록이 일어난 해당 분의 중간 1분봉은 부분봉이므로 장기 보합 계산에서 제외한다.
- 이후 정상적으로 완성된 1분봉만 사용한다.
- 부분봉, 비연속 1분봉, sequence gap, 재접속 직후 불완전 봉 등 데이터 연속성 훼손은 미래정보 없이 무효 처리한다.

### 2.2 rolling window

- 시간축은 그대로 **30 / 60 / 90 / 120 / 150 / 180 / 210 / 240분**을 유지한다.
- 30분은 연구·비교용이며, 보합 박스 최초 생성 최소 시간은 **60분**이다.
- 매 완료 1분봉마다 최근 각 시간축의 rolling window를 다시 계산한다.
- 박스가 아직 없고 여러 시간축이 동시에 보합조건을 통과하면 v2.3.2처럼 가장 긴 통과 horizon을 사용해 최초 박스를 만든다.

### 2.3 보합 조건과 고정 박스

v2.3.2 첫 연구 기준을 그대로 유지한다.

- 최소 보합 인정시간: `BALANCE_ALERT_MIN_DURATION = 60`
- 박스 폭: `BALANCE_MAX_RANGE_PCT = 1.50`
- 순변화율 절댓값: `BALANCE_MAX_ABS_NET_CHANGE_PCT = 0.50`
- 추세 기울기 절댓값: `BALANCE_MAX_ABS_SLOPE_PCT_PER_MIN = 0.010`

최초 `BASE_READY`(보합완성) 시점에 해당 통과 window의:

- `base_high` = 완료 1분봉 high의 최댓값
- `base_low` = 완료 1분봉 low의 최솟값

을 고정한다.

이후 90·120·150분 등 더 긴 rolling window가 통과해도 **고정된 base_high/base_low를 다시 움직이지 않는다.**

### 2.4 돌파·무효 조건

- 완료봉 종가가 고정 상단 +0.10% 이상이면 `BREAKOUT_WATCH`(돌파 관찰)로 간다.
- 다음 완료봉도 원래 박스 상단 이상을 유지하면 `BASE_BREAKOUT`(보합돌파) 확정한다.
- 확정 뒤 다음 정상 tick에서 기존 63-grid 가상진입을 생성한다.
- 첫 돌파 시도 후 다음 완료봉이 상단을 유지하지 못하면 **돌파 실패일 뿐 박스 자체는 종료하지 않는다.** 이후 재돌파를 기다릴 수 있다.
- 완료봉 종가가 고정 하단 -0.20% 아래로 내려가면 `BASE_EXPIRED`(보합종료), reason=`LOW_BREAK`.
- 데이터 연속성이 훼손되면 해당 박스를 신뢰하지 않고 종료한다.
- 15:30 세션 종료 시 열린 박스는 종료한다.
- 신규 가상진입 cutoff 15:10, 장기 보합 관찰 종료 15:30은 그대로 유지한다.

## 3. 다음 버전에서 확정 반영할 Telegram 변경

### 3.1 최초 보합완성 표시만 반복하지 않는다

v2.3.2는 예를 들어 10:20에 60분 보합완성이 발생하면 10:30, 11:00, 11:30 누적 메시지에서도 최초의 `60분 보합완성 - 10:20`이 그대로 남는다.

다음 버전에서는 **현재 살아 있는 박스의 실제 경과시간**을 갱신해서 표시한다.

예시:

```text
10:20  최초 60분 보합완성
10:30  A종목 - 보합 70분째 / 최초완성 10:20 / 돌파대기
11:00  A종목 - 보합 100분째 / 최초완성 10:20 / 돌파대기
11:30  A종목 - 보합 130분째 / 최초완성 10:20 / 돌파대기
```

따라서 Telegram 표시시간은 60/90/120분 같은 horizon 단계에만 맞추지 않는다. **발송 기준시각에서 계산 가능한 실제 분 단위 경과시간**을 우선 표시한다.

### 3.2 보합 시작시각을 명시적으로 보존한다

정확한 현재 지속시간을 계산할 수 있도록 최초 박스 생성 시 아래 값을 저장하거나 재현 가능하게 한다.

- `base_start_time` (보합 박스 시작시각): 최초 BASE_READY를 만든 rolling window의 첫 정상 완료봉 시작시각
- `base_ready_time` (최초 보합완성시각)
- `initial_ready_duration_min` (최초 완성 horizon, 예: 60/90)
- `base_high`, `base_low`
- `box_id`

예: BASE_READY가 10:20이고 최초 horizon이 60분이면 `base_start_time`은 해당 60분 window의 시작인 약 09:20이다.

### 3.3 “현재 몇 분째”의 정의

`current_balance_elapsed_min`은 **박스 시작시각부터 해당 Telegram cutoff 시각까지 박스가 유효하게 살아 있는 시간**으로 계산한다.

단, 미래정보 누수를 막기 위해 각 30분 요약은 반드시 **그 cutoff 시점까지 발생한 이벤트만으로 당시 상태를 재구성**해야 한다.

예를 들어 프로그램이 11:05에 밀린 요약을 한꺼번에 만든다고 해도:

- 10:30 요약은 10:30 현재 상태와 70분을 사용
- 11:00 요약은 11:00 현재 상태와 100분을 사용

해야 하며, 둘 다 11:05 현재 값으로 덮어쓰면 안 된다.

### 3.4 60·90·120분 개별 보합 알림

기존 `BASE_MATURE`(보합 성숙) 원장은 계속 보존한다.

사용자 최신 결정에 따라 장기 보합 개별 Telegram은 돌파 시점에만 보내지 않는다.

- 최초 60분 보합완성: **즉시 개별 알림 1회**
- 90분 보합 유지 확인: **즉시 개별 알림 1회**
- 120분 보합 유지 확인: **즉시 개별 알림 1회**
- 보합돌파 확정 및 가상진입: **즉시 개별 알림 1회**
- 단순 보합종료(하단이탈 등): 개별 알림 없이 30분 누적 알림에서 종료상태 표시

90분·120분 알림은 같은 박스에서 각 milestone당 한 번만 전송한다. 재시작·지연전송에서도 중복되면 안 된다.

개별 알림 예시:

```text
🟨 장기 보합 유지

A종목
종목코드 : 000001

⏱ 보합
- 시작 : 09:20
- 현재 : 90분
- 최초완성 : 10:20

📦 박스
- 상단 : 51,000원
- 하단 : 50,300원
- 박스폭 : 1.39%

상태 : 돌파대기

연구용 관찰
실제주문 없음
```

30분 누적 Telegram에서는 별도로 현재 실제 지속시간을 계속 갱신해 `보합 N분째`로 표시한다.

**150·180·210·240분에서도 개별 milestone 알림을 추가할지는 아직 확정하지 않는다.** 해당 horizon의 내부 연구·원장 기록은 계속 유지한다.

## 4. 보합이 깨졌을 때 Telegram 처리

보합이 종료된 종목을 누적 메시지에서 즉시 삭제하지 않는다.

당일 누적 알림에 아래 정보를 남긴다.

- `보합종료`
- 종료시각
- 총 보합 지속시간
- 종료 사유

예시:

```text
[장기 보합 돌파]
1. A종목(000000) - 보합 100분째 / 최초완성 10:20 / 돌파대기
2. B종목(111111) - 보합종료 11:07 / 총 86분 / 하단이탈
3. C종목(222222) - 보합 135분 → 보합돌파 11:24
```

종료 사유의 사용자 표시명은 최소한 다음처럼 명확히 변환한다.

- `LOW_BREAK` → **하단이탈**
- sequence gap / reconnect / invalid bar 등 → **데이터연속성훼손**
- `SESSION_END` → **장종료**

내부 영문 reason은 원장에 그대로 보존하고 Telegram만 한국어로 표시해도 된다.

## 5. 보합돌파가 발생했을 때

`BASE_BREAKOUT`이 확정되면 해당 박스는 사용자 관점에서 더 이상 `보합 N분째 / 돌파대기` 상태가 아니다.

다음 30분 누적 알림부터는 해당 종목을 **보합돌파 완료 상태**로 표시한다.

예시:

```text
A종목(000000) - 보합 135분 → 보합돌파 11:24
```

여기서 135분은 박스 시작시각부터 돌파 확정시각까지의 지속시간이다.

돌파 완료 뒤 단순 세션 종료 때문에 다시 `보합종료`로 사용자에게 표시하지 않는다. 사용자 표시 terminal 상태는 `보합돌파`를 우선한다. 내부 cleanup/SESSION_END 이벤트는 필요하면 원장에 남긴다.

## 6. 30분 누적 알림 구조 유지

알림 발송 시각은 v2.3.2 그대로 유지한다.

`09:30, 10:00, 10:30, 11:00, 11:30, 12:00, 12:30, 13:00, 13:30, 14:00, 14:30, 15:00, 15:30`

같은 Telegram 채팅방에서 전략별 말풍선을 분리하는 원칙도 유지한다.

발송 순서:

1. BASE
2. FIRST 75 PASS
3. PULLBACK STRUCTURE ENTRY
4. SNAPSHOT 30 → 240분
5. 장기 보합 돌파

`[장기 보합 돌파]`는 해당 cutoff 기준 당일 누적 상태를 보여준다.

## 7. 상태·원장 최소 보강 요구

다음 버전은 기존 v2.3.2 상태기계를 전면 재작성하지 말고 최소 수정한다.

필요한 값은 최소한 다음 중 하나의 방식으로 영속 복구 가능해야 한다.

- `base_start_time`
- `base_ready_time`
- `initial_ready_duration_min`
- `base_end_time`
- `base_end_reason`
- `breakout_time`
- `balance_elapsed_min`

기존 `pullback_balance_evaluations_v232.csv`, `pullback_balance_events_v232.csv`, checkpoint, signal ledger와의 호환성을 우선한다. 파일 버전명을 올릴지는 구현 시 결정하되 과거 v2.3.2 파일을 깨뜨리지 않는다.

재시작 후에도 이미 확정된 박스의 시작시각·종료시각·돌파상태를 복구해 같은 종목/박스의 Telegram 상태가 되돌아가거나 중복되지 않아야 한다.

- 같은 종목에서 첫 보합 박스가 종료된 뒤 새 박스를 다시 만들었을 때 Telegram에 여러 box episode를 어떻게 표시할지
- 보합종료를 즉시 별도 Telegram으로도 보낼지 여부
- `보합 N분째`에 박스 상·하단 가격/폭까지 같이 표시할지 여부
- 150·180·210·240분에도 90·120분처럼 개별 milestone 알림을 추가할지 여부
- 장기 보합 자체의 조건값 1.50%, ±0.50%, ±0.010%/분의 조정
- rolling-window 방식 대신 실제 보합 시작점 탐지형 알고리즘으로 변경할지 여부
