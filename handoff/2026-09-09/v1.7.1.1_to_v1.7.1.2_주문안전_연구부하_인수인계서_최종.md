## 1. 이번 릴리스의 최우선 목표

## 4. import·미정의 이름 재발 방지

- `import uuid`를 명시한다.
- 모든 신규 표준·외부 라이브러리는 import 목록과 실제 사용 위치를 함께 검토한다.
- compile만으로 잡히지 않는 미정의 global name을 정적검사한다.
- 실제 주문을 mock한 cold-start 및 end-to-end 테스트를 수행한다.
- 함수 존재 여부나 정책 판정만 검사하지 말고 `가격 tick → TP/SL → submit_live_exit → 검증 → SELL → 주문번호 기록`을 호출한다.
- 안전한 `make_exit_attempt_id()`를 두고 UUID 생성 실패도 포착한다. UUID 오류가 REST fallback 생성까지 막지 않도록 기존 의존성만 사용하는 대체 ID를 준비한다.
- import 누락·미정의 이름을 발견하지 못하는 회귀테스트는 통과로 간주하지 않는다.

## 5. 매도 투트랙 확정 구조

### 5.1 FAST_CACHE_EXIT

캐시 매도는 유지한다.

- TP/SL 0.5%p 접근 시 캐시 준비
- 직전 완료 후 30초 주기 갱신
- 목표·손절 0.2%p 이내이고 캐시가 10초 초과면 우선 갱신
- 최대 45초 이내 유효 캐시만 허용
- 보유수량, 매도가능수량, 외부 미체결 매도, cache generation, position version, exit attempt가 모두 일치해야 사용
- 주문 직전 generation·version·중복주문을 다시 확인

유효하면 추가 REST 계좌조회 없이 확인된 자동관리수량을 시장가 SELL 한다.

### 5.2 SAFE_REST_EXIT

다음 상황에서는 캐시를 폐기하고 직전 검증 방식으로 broker를 새로 조회한다.

- 캐시 없음·만료
- generation·position version 불일치
- 보유·매도가능수량 불일치
- 외부 미체결 주문 의심
- 캐시 갱신 실패
- uuid, 자료형, 필드누락 등 캐시·새 주문 전처리 예외
- cache worker·dispatcher 처리 예외

REST에서 보유수량·매도가능수량·미체결을 모두 확인한 뒤 자동관리수량과 조정해 시장가 SELL 한다.

### 5.3 공통 주문 coordinator

- 두 경로는 cache 전처리와 REST 전처리를 분리한다.
- 최종 SELL 제출·주문 원장·중복방지는 공통 coordinator를 사용한다.
- fallback은 과거 `.ipynb`를 런타임에 재실행하는 방식이 아니다.
- 현재 상태모델과 호환되는 직전 검증 REST 함수로 구현한다.
- 새 경로와 fallback이 같은 미검증 helper·executor에 묶여 동시에 실패하지 않게 한다.

## 6. fallback 적용 경계

### SELL API 호출 전 오류

1. 오류를 해당 종목 경계에서 포착
2. 신규매수 SAFE HALT
3. 캐시·신규 경로 폐기
4. `SAFE_REST_EXIT` 생성
5. broker 실조회
6. 확인된 수량 시장가 매도
7. 주문·체결 추적

### SELL API 호출 후 접수 여부가 불명확한 오류

timeout, 연결단절, 주문번호 누락은 즉시 fallback 재주문하지 않는다.

1. `ORDER_STATUS_UNKNOWN`
2. 신규매수 SAFE HALT
3. broker 주문·미체결·체결·보유수량 조회
4. 기존 주문 발견 시 추적
5. 주문 미접수와 보유수량 유지가 명확할 때만 새 SELL 허용

### 신규 BUY 경로 오류

매수는 이전 방식으로 강행하지 않는다. 해당 신규매수를 취소·차단하는 fail-closed 원칙을 적용한다.

## 7. SAFE HALT 의미

SAFE HALT는 신규 실제매수를 막는 기능이다.

SAFE HALT 중에도 계속해야 하는 작업:

- 기존 포지션 실시간 가격감시
- TP/SL 판단
- 캐시 또는 REST 청산
- 미체결·부분체결 추적
- 주문상태 복구
- broker 잔고 동기화

매도 오류가 발생했다고 기존 보유종목의 자동관리를 종료하지 않는다.

## 8. 오류별 확정 처리

| 상황 | 처리 |
|---|---|
| 캐시 단순 만료 | REST 검증 후 매도 |
| uuid·캐시 코드 예외 | 신규매수 HALT + REST fallback |
| REST 일시 오류 | `EXIT_RECOVERY`, 제한적 재조회 |
| REST 지속 오류 | 신규매수 차단 유지, 주기 재조회·긴급 수동확인 |
| 명확한 SELL 거부 | REST로 원인·수량 재확인 후 제한적 재시도 |
| SELL 응답 불명확 | 재주문 금지, broker 상태 먼저 확인 |
| 외부 미체결 매도 | 중복 SELL 금지, 기존 주문 추적 |
| 부분체결 SELL | delta만 반영, 기존 잔량 추적 |
| 부분체결 BUY 중 TP/SL | BUY 잔량 취소 확인 후 체결분 청산 |
| live_state 저장 실패 | SELL 계속, 신규매수 HALT, 저장 재시도 |
| 연구 오류·과부하 | 연구만 축소, 실제 주문 계속 |
| WebSocket 종목 처리 오류 | 해당 이벤트 격리, 연결 유지 |

## 9. 매도 dispatcher·WebSocket 보강

- dispatcher 최상단에 예외 경계를 둔다.
- 한 worker 예외로 단일 dispatcher Future가 종료되지 않게 한다.
- 예상 밖 매도 예외는 `EXIT_RECOVERY`와 REST fallback으로 넘긴다.
- dispatcher heartbeat, 현재 처리 attempt, 큐 대기시간을 기록한다.
- watchdog이 dispatcher 비정상을 감지하면 신규매수 HALT 후 안전하게 복원한다.
- 종목별 `handle_realtime_price()` 예외를 WebSocket 수신 루프 밖으로 전파하지 않는다.
- 주문체결 이벤트 처리와 가격 이벤트 처리를 각각 격리한다.
- 반복 오류는 최초 즉시 알림 후 주기 요약하되, 중요한 최초 오류를 숨기지 않는다.

## 10. 트리거 직후 순서

현재의 `트리거 → 동기식 live_state 저장 → 큐 등록` 구조를 개선한다.

목표 순서:

1. TP/SL 트리거 확정
2. 안전한 attempt ID 생성
3. 메모리 상태를 원자적으로 `EXIT_TRIGGERED`로 전환
4. 손절 우선순위 매도 큐 즉시 등록
5. 주문 의도 journal 또는 중요 state 저장 시도
6. 저장 실패를 주문 경로에서 격리하고 SELL은 계속

지속성 저장과 즉시 제출 사이의 crash window를 검토해, 주문 의도 journal을 작고 빠르게 유지한다.

## 11. 매도 우선순위

broker/API 작업 우선순위:

1. 손절 SELL
2. 익절 SELL
3. `ORDER_STATUS_UNKNOWN` 복구
4. 부분체결 BUY 잔량취소·체결분 청산
5. 계좌 캐시 갱신
6. 신규 BUY precheck
7. 정기 계좌 동기화

매도 REST 검증이 신규매수·정기조회 뒤에서 기다리지 않도록 전용 실행영역 또는 우선순위 scheduler를 사용한다. 키움 API 호출 간격 제한은 유지한다.

## 12. 주문 직전 invariant

SELL 바로 전에 다음을 다시 확인한다.

- 동일 `exit_attempt_id`
- 허용된 EXIT 상태
- `exit_order_in_progress=True`
- 내부 SELL 미체결 없음
- 외부 SELL 미체결 없음
- `pending_auto_sell_qty` 중복 없음
- cache generation·position version 일치 또는 최신 REST snapshot 사용
- `qty > 0`
- `qty <= auto_managed_qty`
- `qty <= broker sellable_qty`
- shutdown 이후 신규 submit 아님

하나라도 위반하면 SELL을 강행하지 않고 REST 재검증 또는 주문상태 복구로 이동한다.

## 13. 청산 상태 모델

최소 다음 상태를 명시적으로 구분한다.

- `EXIT_TRIGGERED`
- `EXIT_VALIDATING_CACHE`
- `EXIT_VALIDATING_REST`
- `EXIT_SUBMITTING`
- `EXIT_PENDING`
- `EXIT_PARTIAL`
- `EXIT_RECOVERY`
- `ORDER_STATUS_UNKNOWN`
- `MANUAL_INTERVENTION_REQUIRED`
- `EXIT_FILLED`

`EXIT_ERROR`를 기록하고 자동관리를 포기하는 방식은 금지한다. 복구 가능·상태 불명확·수동개입 필요를 구분한다.

## 14. 수동·외부 청산 손익 복구

broker 보유수량이 0이 됐다고 포지션만 제거하지 않는다.

- 체결내역에서 실제 체결수량·평균체결가·체결시각 조회
- `MANUAL_EXIT` 또는 `EXTERNAL_EXIT`로 `live_trades` 기록
- gross와 추정비용 차감 net 손익 반영
- 확인 전에는 임의 가격으로 확정하지 않고 `RECONCILIATION_PENDING`
- 일부 수동매도는 외부 물량·자동관리 잔량과 미체결을 재조정

## 15. 매수 지연 보완

- signal time, precheck queue start, precheck start/end, order time을 분리 기록
- 매도 검증보다 BUY precheck 우선순위를 낮춘다.
- 주문 직전 현재가·신호 나이를 재검증한다.
- 오래된 신호는 이전 방식으로 강행하지 않고 매수를 취소한다.
- 신호 최대 유효시간·허용 가격변동폭은 별도 데이터 근거 없이 전략값으로 임의 확정하지 않는다. 우선 계측·보수적 guard로 구현하고 문서 충돌 시 사용자 확인을 받는다.

- 경량화한 ENTRY_PATH·POST_EXIT

실제 주문 판단·제출 이후에만 연구 snapshot을 처리한다.

## 18. 연구 저장·checkpoint

- 169개 결과를 20시 종료 시점에만 저장하지 않는다.
- 가상진입 발생 즉시 ENTRY 이벤트를 저장한다.
- TP/SL 조합 종료 시 같은 틱의 종료 결과를 batch 저장한다.
- 열린 핵심 연구 상태는 30초 주기 atomic checkpoint를 목표로 한다.
- 정상 종료 시 남은 조합을 `TIME_EXIT`로 저장한다.
- 비정상 종료 후 checkpoint로 복구하거나 `PARTIAL_CRASH`로 명시한다.
- 매 틱 169행을 CSV로 쓰지 않는다.
- 연구 checkpoint·CSV는 실제 주문과 분리된 저우선 writer가 처리한다.

## 19. 연구 부하 축소

2026-09-09 종료 직전 연구 `compute_drop`이 분당 약 5천~6천 건이었다. coalescing이 동작했지만 생산량이 처리능력을 크게 초과했다.

- 종목별 최신 연구 틱 병합
- P2 상세 데이터부터 축소
- 핵심 열린 가상포지션의 TP/SL 결과는 유지
- 신규 저우선 Shadow 생성 중단
- 반복 부하 로그는 1분 요약
- queue 크기·메모리·처리지연 기록
- 연구 queue·writer·lock을 실거래와 분리
- 연구 오류가 실거래 WebSocket·주문 worker로 전파되지 않게 한다.

## 22. heartbeat와 외부 watchdog

프로그램 내부 heartbeat에 다음을 기록한다.

- main loop 마지막 생존시각
- WebSocket 마지막 수신시각
- 주문체결 스트림 마지막 수신시각
- exit dispatcher 마지막 생존시각
- 연구 worker 마지막 생존시각
- 현재 보유·청산 종목 수
- 주문·연구 queue 크기
- 메모리 사용량

프로세스가 완전히 죽은 뒤에는 같은 프로세스가 텔레그램을 보낼 수 없다. 종료 즉시 알림은 별도 프로세스·OS 작업 또는 외부 watchdog이 필요하다. v1.7.1.2 내부 heartbeat만으로 외부 종료 알림이 보장된다고 표현하지 않는다. 자동 재시작은 broker 보유·미체결 동기화 없이 수행하지 않는다.

## 26. 구현상 한계와 금지사항

- 소프트웨어만으로 모든 broker·네트워크·PC 장애에서 체결을 절대 보장할 수는 없다.
- REST fallback도 broker 조회와 SELL API 자체가 고장 나면 주문할 수 없다. 이때 신규매수 차단, 재조회, 긴급 수동확인이 최종 안전조치다.
- 주문 접수 여부가 불명확한 상황에서 빠른 청산을 이유로 중복주문하지 않는다.
- 미확인 수량을 추정해 매도하지 않는다.
- 캐시 속도를 위해 broker 수량·미체결·중복방지 invariant를 제거하지 않는다.
- 프로그램 내부 heartbeat를 외부 crash 알림으로 과장하지 않는다.
- 주문 보완과 동시에 실제 진입전략·TP/SL을 변경하지 않는다.

## 27. 최종 확정 문장

> v1.7.1.2는 캐시 매도를 1차 경로로 유지한다. 신규 매도 경로가 SELL API 호출 전에 실패하면 신규매수를 즉시 SAFE HALT하고 직전 검증 REST 방식으로 broker 보유수량·매도가능수량·미체결을 새로 확인해 기존 포지션 청산을 계속한다. SELL 접수 여부가 불명확하면 중복주문하지 않고 broker 상태 확인을 우선한다. 연구와 파일 기록은 실제 주문보다 낮은 우선순위로 축소·격리한다.
