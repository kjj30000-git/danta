# 3. 사용자 운용 성향과 전략 설계 원칙

사용자는 최대수익만 추구하기보다 다음 상황을 줄이는 쪽에 더 큰 비중을 둔다.

```text
한때 수익 또는 손익분기 기회가 있었던 종목이
장시간 횡보·하락한 뒤 최종 -1.50% 손절로 끝나는 상황
```

따라서 v1.6.10은 다음 구조로 운용한다.

```text
강한 종목       → +2.50% TP까지 보유
한때 +1.00% 도달 → 이후 +0.40%까지 밀리면 수익보호 청산
정오까지 약한 종목 → 손실에서 강제청산하지 않고 +0.40% 회복 시 청산
초기 실패 종목   → 기존 -1.50% SL 유지
장 마감 미청산   → 15:20 강제청산 유지
```

다만 승률을 높이기 위해 작은 이익만 반복하면 기대수익이 오히려 나빠질 수 있다.

제비용을 약 0.23%로 보면:

```text
+0.40% 보호청산의 예상 비용 후 수익률 ≈ +0.17%
-1.50% 손절의 예상 비용 후 수익률 ≈ -1.73%
```

즉 작은 보호이익 약 10회가 손절 1회를 겨우 상쇄하는 구조다. 따라서 보호청산은 심리적 만족이 아니라 **순 기대값과 순 Profit Factor**로 계속 검증해야 한다.

# 5. 비용 반영 성과표 — 앞으로의 기본 규칙

사용자가 확인한 왕복 제비용은 거래대금 대비 약 **0.23%**다.

연구·요약 보고서에 다음 상수를 추가한다.

```python
ESTIMATED_ROUND_TRIP_COST_PCT = 0.23
```

중요:

- 실전 TP/SL·수익보호 트리거는 **실제 평균체결가 대비 비용 제외 수익률**로 판단한다.
- `+0.40%`는 비용 후 순수익률이 아니라 **비용 제외 수익률**이다.
- 성과평가에서만 0.23%를 차감한 추정 순수익률을 함께 계산한다.
- 실제 체결 지연과 slippage로 `+0.40%` 트리거 후 체결수익률이 더 낮아질 수 있다.

모든 기본 성과표에 최소 다음을 표시한다.

```text
trades
wins / losses
win_rate
gross_return_pct_sum / mean
estimated_net_return_pct_sum / mean
gross_pnl_won
estimated_net_pnl_won
gross_profit_factor
net_profit_factor
exit_reason별 건수·손익
```

추정 순수익률:

```python
estimated_net_return_pct = gross_return_pct - ESTIMATED_ROUND_TRIP_COST_PCT
```

추정 순손익은 가능하면 실제 체결 매수금액을 사용한다.

```python
estimated_cost_won = actual_invested_amount * 0.23 / 100
estimated_net_pnl_won = gross_pnl_won - estimated_cost_won
```

# 7. 금액·횟수 고정 잠금 제거 — 확정 변경

v1.6.9의 `validate_live_trading_config()`에는 다음 고정값 잠금이 있다.

```text
LIVE_MAX_STOCKS == 5
LIVE_TRADE_AMOUNT_WON == 3_000_000
LIVE_TOTAL_BUDGET_WON == 18_000_000
LIVE_DAILY_MAX_LOSS_WON == 300_000
```

이 때문에 사용자가 첫 셀에서 종목당 금액을 100만원으로 바꾸자 `ValueError`가 발생했다.

v1.6.10에서는 위 **정확한 숫자 일치 검증을 전부 제거**한다. 다음과 같은 논리적 안전검증만 유지한다.

```python
if not isinstance(LIVE_MAX_STOCKS, int) or LIVE_MAX_STOCKS <= 0:
    raise ValueError("LIVE_MAX_STOCKS는 1 이상의 정수여야 합니다.")

if LIVE_TRADE_AMOUNT_WON <= 0:
    raise ValueError("LIVE_TRADE_AMOUNT_WON은 1원 이상이어야 합니다.")

if LIVE_TOTAL_BUDGET_WON <= 0:
    raise ValueError("LIVE_TOTAL_BUDGET_WON은 1원 이상이어야 합니다.")

if LIVE_TOTAL_BUDGET_WON < LIVE_TRADE_AMOUNT_WON:
    raise ValueError("총 운용예산이 종목당 매수예산보다 작습니다.")

if LIVE_DAILY_MAX_LOSS_WON <= 0:
    raise ValueError("LIVE_DAILY_MAX_LOSS_WON은 1원 이상이어야 합니다.")
```

또한 v1.6.9 회귀테스트의 다음 고정 assertion도 일반화한다.

```text
3,000,000원 고정 assertion 제거
18,000,000원 고정 assertion 제거
300,000원 고정 assertion 제거
5종목 고정 assertion 제거
297주 고정 수량 assertion 제거
```

대신 여러 조합을 검사한다.

```text
종목당 1,000,000 / 최대 5회 / 총 6,000,000 → 통과
종목당 2,000,000 / 최대 3회 / 총 7,000,000 → 통과
종목당 금액 0 → 실패
횟수 0 또는 소수 → 실패
총 예산 < 종목당 금액 → 실패
daily loss <= 0 → 실패
```

사용자가 자유롭게 바꿀 수 있다는 것은 broker 잔고보다 많이 주문할 수 있다는 뜻이 아니다. 기존 broker 현금·주문가능금액·총 committed amount 검증은 그대로 유지한다.

# 8. 실전 TP/SL — 확정 변경

v1.6.9:

```text
LIVE_STRATEGY = T200_S150
TP +2.00% / SL -1.50%
```

v1.6.10:

```text
LIVE_STRATEGY = T250_S150
TP +2.50% / SL -1.50%
```

`EXIT_STRATEGIES`의 기존 169 grid 안에 `T250_S150`이 있으면 그 정의를 재사용한다. 별도의 중복 전략 정의를 만들지 않는다.

검증:

```python
rule = EXIT_STRATEGIES[LIVE_STRATEGY]
if rule != {"tp": 2.5, "sl": -1.5}:
    raise ValueError("T250_S150 정의가 +2.50/-1.50에서 변경되었습니다.")
```

TP를 +2.50%로 높인 근거:

- 지금까지 FIRST_75_PASS 표본에서 TP +2.00~+2.75 구간의 승패 수는 동일했다.
- 비용 0.23%를 고려하면 `+2.00/-1.50`은 1승 1패 순손익이 거의 손익분기다.
- 현재 표본의 비용 차감 평균과 Profit Factor는 `+2.50/-1.50`이 `+2.00/-1.50`보다 개선됐다.
- 다만 표본이 매우 작으므로 +2.75% 또는 더 좁은 SL을 바로 실전에 적용하지 않는다.

# 10. 수익보호 — 다음 장 실제 ON 시험

## 10-1. 확정 규칙

다음 장 수익보호는 켠다.

```python
LIVE_PROFIT_PROTECT_ENABLED = True
LIVE_PROFIT_PROTECT_ARM_PCT = 1.00
LIVE_PROFIT_PROTECT_FLOOR_PCT = 0.40
```

규칙:

```text
실제 평균매수가 대비 수익률이 한 번이라도 +1.00% 이상 도달
→ 해당 포지션의 수익보호 상태를 영구 armed
→ 이후 현재 수익률이 +0.40% 이하로 내려오면 전량 시장가 청산
→ exit reason = PROFIT_PROTECT
```

예:

```text
매수 직후 +1.90% 도달
TP +2.50%에는 도달하지 못함
이후 +0.40%까지 하락
→ PROFIT_PROTECT 매도 제출
```

`+1.00%` 도달 여부는 한 번 armed되면 가격이 다시 내려와도 취소하지 않는다.

## 10-2. 기준 가격과 상태

수익률 기준가는 신호가나 paper 진입가가 아니라 **broker 실제 가중평균 매수체결가**다.

```python
gross_return_pct = (current_price / actual_avg_entry_price - 1.0) * 100
```

포지션별 최소 상태:

```text
max_return_pct
min_return_pct
profit_protect_armed
profit_protect_armed_time
profit_protect_armed_price
profit_protect_floor_pct
profit_protect_trigger_time
profit_protect_trigger_price
profit_protect_trigger_return_pct
```

이 값들은 `live_state`에 저장하며 커널·프로그램 재시작 후에도 유지한다.

## 10-3. ON/OFF 의미

```text
True  → 실제 포지션에 PROFIT_PROTECT 청산 적용
False → 실제 청산에는 적용하지 않음
```

단, False여도 다음 반사실 연구는 계속 기록한다.

```text
만약 +1.00/+0.40 보호를 썼다면 언제 청산됐는가
보호 후 원래 TP/SL 결과는 무엇이었는가
보호가 회피한 손실 또는 놓친 추가상승은 얼마인가
```

## 10-4. 냉정한 평가

현재 수익보호는 검증 완료 전략이 아니다.

- 실제 정책 표본에서 현대약품·KB금융 같은 손실을 줄일 가능성이 있다.
- 반대로 SK이노베이션·금호전기처럼 흔들린 뒤 재상승한 승자를 너무 일찍 자를 수 있다.
- 과거 표본의 거친 반사실 계산에서는 보호 적용 수익합계가 오히려 소폭 낮아질 가능성도 확인됐다.

따라서 다음 장에는 종목당 100만원 수준으로만 켜고, 끈 경우의 결과를 반드시 동시에 남긴다.

# 11. 수익보호 activation 1.00%를 유지하는 이유

FIRST_75_PASS 전체 손실 9건의 MFE 분포:

```text
MFE >= +0.75% : 5 / 9
MFE >= +1.00% : 4 / 9
MFE >= +1.10% : 3 / 9
MFE >= +1.25% : 2 / 9
MFE >= +1.50% : 1 / 9
```

실제 정책에 가까운 손실 4건에서는:

```text
MFE >= +1.00% : 2건
MFE >= +1.10% : 1건
MFE >= +1.25% : 0건
```

따라서 +1.00%는 지나치게 낮다고 단정할 수 없다. +1.25% 이상으로 올리면 보호 대상 자체가 너무 적어진다.

다음 장 실제값은 +1.00%로 유지하되 연구에서는 동시에 다음 activation을 비교한다.

```text
+0.75%
+1.00%
+1.25%
+1.50%
```

각 activation의 floor는 우선 +0.40%로 통일한다.

# 13. 청산 판정 우선순위와 주문 중복 방지

실시간 가격 처리의 개념적 우선순위:

```text
1. 기존 주문 진행·position 상태 확인
2. 기본 TP +2.50%
3. 기본 SL -1.50%
4. 이미 확정된 NOON_RECOVERY_WAIT의 +0.40% 회복
5. 수익보호 arm 또는 +0.40% floor 이탈
6. 15:20 강제청산
```

단, 정오 평가 시점에는 먼저 `profit_protect_armed` 여부를 확인한 후 NOON 대상을 확정한다.

필수 안전조건:

- 동일 가격 event에서 청산사유가 둘 이상이어도 주문은 한 번만 제출한다.
- 기존 `status`, submit intent, pending order, `exit_order_no` 검증을 재사용한다.
- 부분체결 BUY 중 청산조건이 발생하면 기존 `request_entry_cancel_for_exit()` 흐름을 재사용한다.
- 시장가 매도 전 broker sellable precheck를 생략하지 않는다.
- 청산사유가 정해진 뒤 fill까지 시간이 걸려도 다른 사유로 중복매도하지 않는다.
- Telegram 실패는 청산·상태전이를 막지 않는다.

권장 구현은 기존 `update_live_position_on_price()`를 최소 확장하는 것이다. 주문 제출 함수 자체를 새로 만들지 말고 기존 `submit_live_exit()`를 사용한다.

# 16. 진입시간 종료 경계 수정

v1.6.9는 문자열 분 단위로 다음과 같이 비교한다.

```python
LIVE_ENTRY_START <= now_hhmm <= LIVE_ENTRY_END
```

이 구현은 `LIVE_ENTRY_END = "09:30"`일 때 09:30:00~09:30:59를 허용한다. 실제로 KB금융 신호는 09:30:42, 주문은 09:30:47, 체결은 09:30:48이었다.

의도한 진입시간은 `09:05:00 이상, 09:30:00 미만`이다.

다음처럼 초 단위로 비교한다.

```python
start_t = time(9, 5, 0)
end_t = time(9, 30, 0)
allowed = start_t <= decision_time.time() < end_t
```

주문 제출 직전 재검증도 같은 exclusive end 함수를 사용한다. 신호 판정 때 통과했더라도 broker precheck 후 주문시각이 09:30:00 이상이면 신규 BUY를 제출하지 않는다.

테스트:

```text
09:04:59 → 차단
09:05:00 → 허용
09:29:59.999 → 허용
09:30:00 → 차단
09:30:42 → 차단
```

# 17. 시작 시 네트워크 오류와 SAFE HALT 보완

2026-09-03 07:23경 관찰:

```text
Kiwoom REST ReadTimeout
Telegram DNS getaddrinfo failed
WebSocket DNS getaddrinfo failed 반복
Startup 계좌검증 실패
SAFE HALT / ORDER_STATUS_UNKNOWN
```

커널을 재시작해도 `live_state`에 저장된 HALT가 복구될 수 있으므로 재시작만으로는 해제되지 않을 수 있다.

v1.6.10 원칙:

1. 단순 시작 네트워크 단절과 실제 주문상태 불명확을 구분한다.
2. 토큰·계좌·보유·미체결 조회에 bounded retry/backoff를 적용한다.
3. Telegram 전송 실패는 로그만 남기고 trading state를 변경하지 않는다.
4. broker 계좌·보유·미체결을 모두 정상 조회하기 전에는 신규주문을 열지 않는다.
5. 실제 미확인 주문 또는 수량 불일치가 있으면 기존 SAFE HALT를 유지한다.
6. 네트워크가 회복되고 broker 상태가 완전히 일치한 경우에만 startup connectivity halt를 자동 해제하거나 비영속 대기로 처리한다.

절대 금지:

```text
ORDER_STATUS_UNKNOWN을 단순 시간경과로 자동 해제
broker 확인 없이 live_state 삭제 또는 빈 상태로 덮어쓰기
실제 포지션이 있는데 신규 장으로 오인
```

가능하면 halt reason을 분리한다.

```text
STARTUP_CONNECTIVITY_WAIT
ORDER_STATUS_UNKNOWN
POSITION_MISMATCH
MANUAL_INTERVENTION_REQUIRED
```
