## 4. 신규 전략 전체 개념

상태 흐름:

```text
CANDIDATE
  ↓
PEAK
  ↓
PULLBACK
  ↓
SUPPORT_CANDIDATE
  ↓
SUPPORT_CONFIRMED
  ├─ PULLBACK_SUPPORT_ENTRY
  ↓
BASE
  ↓
```

`FALLING`은 영구 탈락 상태가 아니다.
하락이 계속되면 지지 타이머를 리셋하고 다시 PULLBACK 관찰을 계속한다.
같은 날 나중에 실제 지지가 만들어지면 다시 SUPPORT_CANDIDATE로 진입할 수 있다.

## 6. 후보는 기존 paper trade 종료 후에도 계속 추적

이번 신규 전략에서 가장 중요한 구조 변경이다.

기존 BASE/FIRST_75의 TP/SL 가상전략이 모두 종료되어도, 그 종목이 눌림 후보로 등록되었다면 **당일 관찰 종료시점까지 가격 추적을 계속한다.**

필수 구현:

- paper position 생명주기와 candidate watcher 생명주기를 분리
- 기존 paper position 종료만으로 WebSocket 실시간 구독을 해제하지 않음
- 종목별 실시간 구독은 reference count 또는 동등한 안전 방식으로 관리
- `paper_position 필요` 또는 `pullback_candidate 필요` 중 하나라도 True면 구독 유지
- 둘 다 필요 없을 때만 unsubscribe
- 같은 종목 중복 subscribe 금지
- 장/프로그램 종료 시 정상 정리

새 전략을 위해 종목마다 반복 REST 조회를 추가하지 않는다.
가능하면 기존 WebSocket 가격 스트림을 재사용한다.

## 8. PEAK 규칙

후보 등록 이후 완료된 1분봉을 기준으로 당일 관찰 고점 `H`를 계속 갱신한다.

```text
H = max(후보 등록 이후 완료 1분봉 high)
```

새로운 고점이 나오면 H를 갱신한다.

아직 SUPPORT/RECLAIM 진입이 발생하지 않은 상태에서 이전 H를 넘어 새로운 고점이 만들어지면 기존 pullback episode를 종료하고 새 H 기준으로 새 episode를 시작한다.

---

## 9. PULLBACK 규칙

고점 H 대비 눌림이 **-1.5% 이상**이면 PULLBACK 상태로 들어간다.

기본식:

```text
pullback_pct = (관찰가격 / H - 1) × 100
PULLBACK 시작: pullback_pct <= -1.5%
```

재현성을 위해 최소 완료 1분봉 low가 H 대비 -1.5% 이하인지 판단 가능해야 한다.

### 9.1 시간대 필터 없음

새 눌림전략에는 다음과 같은 별도 진입시각 제한을 두지 않는다.

- 10:00 이후만
- 11:00 이후만
- 14:40 이전만

등의 전략상 시각 필터는 만들지 않는다.

단, **거래소 세션/프로그램 종료/기존 강제청산 같은 시스템 운영 경계는 전략 시간필터와 별개**이며 부모 안전정책을 유지한다.

### 9.2 눌림 깊이 상한 없음

초기 연구에서 다음을 하드필터로 만들지 않는다.

- -5.5% 이하 탈락
- -6% 이하 탈락
- 기타 임의의 최대 눌림 상한

실제 최대 눌림을 연속값으로 저장한 뒤 데이터로 결정한다.

## 10. 저점 L과 지지영역

PULLBACK 이후 절대 최저가를 계속 기록한다.

```text
raw_pullback_low = min(PULLBACK 이후 완료 1분봉 low)
```

지지 판정은 미세한 한두 틱 때문에 무한 리셋되지 않도록 **0.30% 허용폭**을 사용한다.

### 10.1 유의미한 신저가

현재 지지 기준 저점 `support_anchor_low`보다 새 low가 **0.30%를 초과하여 더 낮으면**:

- 새로운 유의미한 저점으로 인정
- `support_anchor_low` 갱신
- support timer 0으로 리셋
- 상태는 PULLBACK 계속

### 10.2 허용범위 안의 저점

새 low가 기존 support anchor보다 낮더라도 -0.30% 이내라면:

- raw absolute low는 최신 실제값으로 기록
- 같은 지지영역의 retest로 취급
- support timer를 강제로 0으로 리셋하지 않음

## 11. SUPPORT_CANDIDATE

마지막 유의미한 신저가 이후 **3개의 완료 1분봉 동안 -0.30% 초과 하향이탈이 없으면**:

`SUPPORT_CANDIDATE`

로 전환한다.

주의:

- 아직 가상진입하지 않는다.
- 단순히 3분 버틴 것만으로 지지 확정 아님.

## 12. SUPPORT_CONFIRMED

아래 두 조건을 동시에 만족해야 한다.

1. 마지막 유의미한 신저가 이후 **5개의 완료 1분봉 이상** 지지영역 유지
2. 현재 완료 1분봉 종가가 실제 pullback low 대비 **+0.40% 이상 회복**

기본식:

```text
close >= raw_pullback_low × 1.004
```

조건 충족 시:

- `SUPPORT_CONFIRMED`
- `PULLBACK_SUPPORT_ENTRY` 신호 발생

### 12.1 SUPPORT 가상체결

판정을 위해 방금 완료된 1분봉의 종가를 보고 같은 종가에 과거체결한 것으로 기록하지 않는다.

원칙:

- `support_signal_time` = 조건을 확정한 완료봉 시각
- 가상 진입가격 = **신호 확정 후 실제로 관측 가능한 첫 가격**
- 실시간에서는 다음 수신 tick
- 장후 replay에서는 다음 1분봉 open 또는 동등하게 미래누수 없는 첫 가용가격
- signal time과 fill time/price를 분리 저장
- signal-to-fill delay와 entry slippage 저장

세션 종료 등으로 신호 후 체결 가능한 가격이 없다면 신호는 기록하되 `NO_FILL_SESSION_END` 등 명확한 상태로 paper trade는 생성하지 않는다.

## 14. RECLAIM 규칙

SUPPORT_CONFIRMED 이후의 다음 완료봉부터 RECLAIM을 평가한다.

기본 기준:

```text
prior_5m_high = 현재 봉을 제외한 직전 5개 완료 1분봉 high의 최댓값
RECLAIM_CONFIRMED:
current_close >= prior_5m_high × 1.001
```

즉 **직전 5분 고점 +0.10%를 완료 1분봉 종가로 돌파**해야 한다.

조건 충족 시:

- `RECLAIM_CONFIRMED`
- `PULLBACK_RECLAIM_ENTRY` 신호 발생

SUPPORT_CONFIRMED와 같은 완료봉에서 RECLAIM을 동시에 확정하지 않는다.
RECLAIM은 SUPPORT 이후 최소 다음 완료봉부터 평가한다.

### 14.1 RECLAIM 가상체결

SUPPORT와 동일한 미래정보 방지 원칙:

- `reclaim_signal_time` = 조건 확정 완료봉 시각
- 가상 진입 = 신호 확정 이후 첫 가용가격
- signal/fill 시각·가격 분리
- slippage 저장

---

## 15. 거래량은 필터가 아니라 feature

초기 버전에서 거래량 조건을 진입 필수조건으로 두지 않는다.

예시 feature:

```text
reclaim_volume_ratio =
현재 1분 거래량 / 직전 10개 완료 1분봉 거래량 중앙값
```

저장 후 추후 분석에서 유효성이 확인될 때만 필터 승격을 검토한다.

---

## 16. FALLING 처리

하락 중인 종목을 너무 빨리 영구 탈락시키지 않는다.

- 유의미한 신저가가 계속 발생하면 support timer를 리셋
- 상태는 `PULLBACK/FALLING`으로 유지
- 나중에 신저가가 멈추고 3분/5분 지지조건을 만족하면 다시 SUPPORT_CANDIDATE/CONFIRMED 가능
- 당일 영구 INVALID 판정은 이번 초기 전략에서 최소화

---

## 17. 동일종목 신규전략 진입 횟수

당일 종목별:

- `PULLBACK_SUPPORT_ENTRY` 최대 1회
- `PULLBACK_RECLAIM_ENTRY` 최대 1회

SUPPORT 진입 후 같은 support episode에서 나중에 RECLAIM이 발생하면 RECLAIM 전략은 별도로 1회 진입 가능하다.

각 전략은 독립 trade_id를 사용하되 같은 `support_episode_id`를 연결하여 SUPPORT vs RECLAIM 비교가 가능해야 한다.

새 고점으로 새 pullback episode가 생기더라도 해당 전략이 이미 그 종목에서 당일 1회 진입했다면 재진입하지 않는다.

## 18. 169 TP/SL grid

사용자 최종 결정:

**새 두 전략도 기존 169 grid를 사용한다.**

공통 grid:

```text
TP: +1.00% ~ +4.00%, 0.25% 간격 = 13개
SL: -0.50% ~ -3.50%, 0.25% 간격 = 13개
13 × 13 = 169
```

적용:

- BASE: 기존 169 유지
- FIRST_75_PASS: 기존 169 유지
- PULLBACK_SUPPORT_ENTRY: 169 사용
- PULLBACK_RECLAIM_ENTRY: 169 사용

### 18.1 리소스 원칙

후보 등록, PULLBACK, SUPPORT_CANDIDATE 상태에서는 169 grid를 미리 만들지 않는다.

**실제 신규 전략 진입이 확정되고 첫 가용가격으로 가상체결될 때만 169개 전략 상태를 생성한다.**

즉:

```text
후보 관찰 → grid 0
PULLBACK → grid 0
SUPPORT_CANDIDATE → grid 0
SUPPORT 실제 진입 → 169 생성
RECLAIM 실제 진입 → 169 생성
```

기존 연구 queue/batch writer/overload 격리 원칙을 유지한다.

추가 모니터링:

- queue backlog
- writer latency
- WS 처리지연
- candidate 수
- open research strategy count
- minute aggregation delay

연구부하가 증가해도 주문/실시간 안전경로보다 우선해서 blocking 처리하지 않는다.

## 19. 비용과 성과분석

v1.7.0 이후 기준과 동일하게 왕복 추정비용 **0.24%**를 유지한다.

향후 비교의 핵심 4축:

1. BASE
2. FIRST_75_PASS
3. PULLBACK_SUPPORT_ENTRY
4. PULLBACK_RECLAIM_ENTRY

특히 기존 대표 기준 `T250_S150`도 4전략 간 동일조건 비교가 가능하도록 유지한다.

- 고유 진입 표본 = trade_id
- grid 결과 = trade_id + TP + SL

원칙을 유지한다.

## 20. Telegram 개별 신호 알림

### 20.1 표시 전략명

사용자에게 보이는 개별 신호 알림은 아래 4개만 사용한다.

- `[BASE]`
- `[FIRST_75_PASS]`
- `[PULLBACK_SUPPORT_ENTRY]`
- `[PULLBACK_RECLAIM_ENTRY]`

### 20.2 기존 본문 보존

BASE와 FIRST_75_PASS는 **기존 Telegram 후보 알림 본문을 삭제·축약하지 않는다.**

특히 기존에 표시되던 다음 정보도 유지한다.

- WATCH : 60점+
- HISTORY : n초
- 30초 가격
- 60초 가격
- 60초 고점이격 변화
- 현재가/등락률/거래량
- 거래대금 관련 정보
- 당일고가/고점대비
- 점수 및 점수 세부항목
- 기존 나머지 운영 정보

값이 없으면 기존 방식과 호환되게 `N/A` 등으로 안전 표시하며 알림 포맷팅 오류 때문에 프로그램이 중단되지 않게 한다.

변경점은 **기존 본문의 맨 앞에 [전략명] 한 줄을 추가**하는 것이다.

### 20.3 삭제할 기존 문구

다음 안내 블록은 Telegram 개별 후보 알림에서 삭제한다.

```text
가상전략
BASE / PRE_HISTORY / CONFIRM / LIVE_FILTER_SHADOW
각 진입마다 TP 1.00~4.00% × SL -0.50~-3.50%
총 169개 조합 동시추적
```

중요:

- 이 문구만 알림에서 삭제하는 것이며 169-grid 자체를 없애는 의미가 아니다.
- 코드 내 grid 정의/CSV 저장은 위 18절 결정대로 유지한다.

### 20.4 신규 전략 추가 판정 블록

`PULLBACK_SUPPORT_ENTRY`와 `PULLBACK_RECLAIM_ENTRY`는 기존 공통본문 뒤에 판정근거를 추가한다.

SUPPORT 최소 표시:

- 원본후보: BASE / FIRST_75_PASS / BOTH
- 원본후보 발생시각
- 고점 / 고점시각
- 눌림저점 / 저점시각
- 최대눌림
- 저점대비 회복
- 지지 지속
- 지지 허용범위
- Higher Low
- 진입판정 = SUPPORT_CONFIRMED
- 신호시각
- 가상진입시각/가상진입가

RECLAIM 추가 표시:

- 위 SUPPORT 관련 정보
- 직전 5분 고점
- Reclaim 기준 = 직전 5분 고점 +0.10%
- Reclaim 가격
- 거래량비
- 진입판정 = RECLAIM_CONFIRMED
- 신호시각
- 가상진입시각/가상진입가

표시값은 문자열 하드코딩으로 사실과 다른 숫자를 보여주지 말고 실제 runtime state에서 동적으로 생성한다.

## 26. 검증 요구사항 — 이번 버전에서 특히 중요

사용자는 최근 코드 오류 반복 때문에 **한 번에 완성도 있게 수정**하기를 원한다.
따라서 코드 작성 완료 조건을 엄격히 한다.

### 26.1 정적/환경 검증

- 전체 코드셀 compile
- pyflakes 등 미정의-name 검사
- import 누락 검사
- clean-process cold-start
- negative-control로 검사기 자체 검증
- 부모 정의 보존 확인
- `if __name__ == "__main__": run_scanner()` 정확히 1회

### 26.2 전략 상태머신 fixture

최소 아래를 deterministic fixture로 재생한다.

1. BASE만 발생 → candidate_source BASE
2. FIRST75만 발생 → FIRST_75_PASS
3. BASE 후 FIRST75 → BOTH로 승격, candidate 중복 없음
4. FIRST75 후 BASE → BOTH로 승격, candidate 중복 없음
5. -1.49% 눌림 → PULLBACK 아님
6. -1.50% → PULLBACK
7. 지지 2분 → SUPPORT_CANDIDATE 아님
8. 3분 유지 → SUPPORT_CANDIDATE
9. 5분 유지했지만 +0.39% 회복 → SUPPORT_CONFIRMED 아님
10. 5분 +0.40% 회복 → SUPPORT_CONFIRMED
11. -0.30% 이내 retest → timer 유지
12. -0.30% 초과 신저가 → timer reset
13. support 후 prior 5m high +0.09% → RECLAIM 아님
14. +0.10% 종가 돌파 → RECLAIM
15. SUPPORT와 RECLAIM 동일 봉 동시확정 금지
16. 계속 Lower Low → 반복 reset, 영구탈락 아님
17. 이후 지지 형성 → 다시 SUPPORT 가능
18. 새 고점 → 미진입 pullback episode 재설정
19. SUPPORT 전략 동일종목 하루 1회
20. RECLAIM 전략 동일종목 하루 1회

### 26.3 미래정보 누수 검증

- 완료봉 종가로 신호를 확정한 뒤 같은 종가를 과거체결가로 사용하지 않는지 확인
- 다음 가용 tick/open으로 fill되는지 확인
- MFE/MAE/최종청산값이 진입조건에 참조되지 않는지 확인

### 26.4 169-grid 검증

각 실제 신규 진입 episode에서:

- 정확히 169개 strategy 생성
- candidate/pullback 대기 상태에서는 0개
- SUPPORT 1회 = 169
- RECLAIM 1회 = 169
- invalid grid면 반쪽 position을 남기지 않고 원자적으로 실패
- 기존 BASE/FIRST75 169도 회귀 유지

### 26.5 Telegram 검증

- 4개 개별 전략 알림 첫 줄 전략명 정확
- 기존 공통본문 누락 없음
- WATCH/HISTORY/30초/60초/60초 고점이격 변화 유지
- 삭제 대상 169-grid 안내문구가 더 이상 포함되지 않음
- 신규 SUPPORT/RECLAIM 판정값이 runtime 상태와 일치
- N/A 값으로 포맷팅 예외 없음
- 30분 누적알림 09:30~15:30 각 1회
- 같은 분 loop 반복에도 중복발송 없음
- 전략별 동일종목 중복 없음
- 시간순 정렬
- `종목명(종목코드) - HH:MM:SS` 형식 정확
- 날짜 변경 시 초기화

### 26.6 독립 2차 비판적 리뷰

1차 구현/테스트 후 별도 관점으로 다시 검토한다.

특히:

- 구독 해제 race
- 종목 중복구독
- minute rollover 경계
- 09:30/10:30 등 알림 중복
- 장 종료 직전 signal/fill 경계
- 재시작 중복진입
- grid 생성 전후 예외
- queue backlog
