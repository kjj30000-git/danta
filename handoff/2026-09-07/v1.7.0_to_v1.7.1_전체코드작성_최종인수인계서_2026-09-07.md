## 4. P0 오류 1 — 신규 Shadow 타입 비교 예외

### 4-1. 원인

`_optional_positive()`는 과거값이 없을 때 `None`이 아니라 빈 문자열 `""`을 반환한다. 그러나 `maybe_open_new_entry_shadows()`는 `x is not None`만 확인한 뒤 다음 비교를 수행한다.

```python
p30 > 0
```

그 결과 다음 오류가 반복됐다.

```text
TypeError: '>' not supported between instances of 'str' and 'int'
```

### 4-2. 필수 수정

- missing sentinel을 `None`으로 통일하거나 명시적인 boolean/숫자 변환 함수를 사용한다.
- `""`, `None`, NaN, 잘못된 문자열이 숫자 비교로 들어가지 않게 한다.
- 신규 Shadow 한 종류의 예외가 `scan_market()`와 메인루프 전체를 중단시키지 않도록 연구 경로를 격리한다.
- 오류를 조용히 삼키지 말고 mode, 종목, 입력값, rule version을 구조화해 기록한다.
- 결측 history가 정상적인 cold-start 상황임을 회귀시험한다.

필수 테스트:

```text
15/30/60/120/300초 값이 각각 None, "", NaN, 숫자 문자열, 숫자일 때 예외 없음
결측값은 진입 신호가 아니라 관찰 보류
연구 예외가 정상 스캔과 실제 주문 경로를 중단하지 않음
```

`_build_buy_fill_message()`와 `_build_sell_fill_message()`가 실제 설정과 무관하게 다음 문자열을 출력했다.

  - `live_strategy`
  - `take_profit_pct`
  - `stop_loss_pct`

  - `entry_amount_limit`

## 6. P0 청산 지연 — 확인된 실제 원인

네 건의 trigger→주문 제출 지연은 약 9.5~12.65초였다. 주된 구성은 다음과 같다.

- broker 보유·매도가능·미체결 사전조회: 약 5.1~6.8초
- 매도 주문 API: 약 2.6~4.1초
- 두산퓨얼셀은 JW신약 신규매수 precheck가 공용 `BROKER_SYNC_LOCK`을 선점해 매도조회 시작 전 약 4.24초를 추가 대기했다.

따라서 청산과 신규매수의 공용 lock/executor 경합은 P0 결함이다.

필수 구조:

1. 실제 청산 전용 executor를 둔다.
2. 신규매수 precheck와 청산을 같은 `BROKER_SYNC_LOCK` 뒤에 세우지 않는다.
3. 실제 청산을 캐시 갱신, 신규매수, 연구보다 우선한다.
4. 여러 청산이 동시에 발생하면 손절을 익절보다 우선하고, 같은 종류는 trigger 시각 순서로 처리한다.
5. WebSocket callback은 trigger를 원자적으로 고정하고 작업만 제출하며 REST 응답을 기다리지 않는다.
6. 주문 API의 실제 직렬화 요구가 있다면 단순 mutex가 아니라 우선순위 dispatcher를 사용한다.
7. 주문·조회 단계별 latency를 계속 기록한다.

## 7. 확정 청산 방식 — 적응형 broker 사전조회 캐시

### 7-1. 최상위 원칙

가격과 TP/SL 판정은 계속 WebSocket 실시간 시세로 수행한다. 캐시는 가격 캐시가 아니라, 실제 기준가 도달 시 반복하던 느린 broker 계좌 안전검사를 미리 완료해 두는 장치다.

안전검사를 제거하지 않는다. 검증된 최신 계좌상태를 미리 준비하고, 실제 TP/SL 도달 시 조건이 유지됐으면 추가 조회 없이 즉시 시장가 매도한다.

### 7-2. 사용자 설정에 따른 접근 기준

기본 선행폭은 0.5%p이며 특정 T250/S150에 하드코딩하지 않는다.

```python
tp_precheck_pct = max(0.0, take_profit_pct - 0.5)
sl_precheck_pct = min(0.0, stop_loss_pct + 0.5)
```

예시:

| 실제 설정 | 사전조회 시작 |
|---|---:|
| TP +2.50% | +2.00% |
| TP +1.00% | +0.50% |
| TP +0.40% | 진입 직후 |
| SL -1.50% | -1.00% |
| SL -0.80% | -0.30% |
| SL -0.30% | 진입 직후 |

### 7-3. 적응형 갱신 기준 — 확정

| 상태 | 동작 |
|---|---|
| TP/SL 0.5%p 접근구간 진입 | 즉시 최초 비동기 계좌조회 |
| 실제 기준과 0.2~0.5%p 거리 | 직전 조회 완료 후 30초마다 갱신 |
| 실제 기준과 0.2%p 이내 | 캐시 나이가 10초보다 오래됐으면 우선 갱신 요청 |
| 실제 TP/SL 도달 | 진행 중 갱신을 기다리지 않고 유효 캐시로 즉시 주문 |
| 접근구간 이탈 | 캐시는 유지하되 정기 갱신 중단 |
| 체결·주문·수량 변경 | 시간과 무관하게 즉시 무효화 |

확정값:

```text
정기 갱신: 직전 완료 후 30초
청산 허용 최대 캐시 나이: 45초
근접 우선갱신 기준: TP/SL까지 0.2%p 이내이며 캐시 나이 10초 초과
동시 계좌 갱신: 전체 계좌 기준 최대 1개
```

30초를 기다린 뒤 청산한다는 뜻이 아니다. 45초 이내의 검증된 캐시가 있으면 실제 기준가 도달 즉시 매도한다. 30초는 접근상태가 오래 지속될 때 캐시를 재검증하는 주기다.

### 7-4. 전체 프로그램 지연 방지

- 종목별 REST 호출을 반복하지 않고 한 번의 계좌조회로 모든 보유종목을 갱신한다.
- 계좌 캐시 갱신 작업은 최대 1개만 실행한다.
- 진행 중 추가 갱신 요청은 합치며 queue에 누적하지 않는다.
- 완료 후 30초 기준으로 다음 갱신을 예약한다.
- 실제 매도 worker와 캐시 갱신 worker를 분리하고 매도에 우선권을 준다.
- WebSocket 스레드는 갱신 요청만 등록하며 조회하지 않는다.
- 접근 종목이 없으면 주기 조회를 중단한다.
- 5초 고정 반복조회는 채택하지 않는다. 실측 조회가 5~7초여서 API와 프로그램 부하를 만들 수 있다.

### 7-5. 캐시 내용

계좌 snapshot 공통 필드:

```text
verified_at / valid_until / request_id / account_version
조회별 성공 여부 / 조회별 완료시각 / cache_status / invalid_reason
```

종목별 필드:

```text
stock_code / stock_name
account_qty / sellable_qty / auto_managed_qty
pending_sell_qty / pending_buy_qty / pending_order_ids
external_order_detected
position_version
verified_at / valid_until
precheck_status / invalid_reason
```

프로그램 포지션과 함께 대조할 항목:

```text
requested buy qty / cumulative filled qty / avg entry price
auto-managed qty / external qty / partial-fill qty
OPEN 여부 / exit_order_in_progress
entry-time strategy / TP / SL / target / stop
position_version
```

broker 보유수량과 미체결 주문이 서로 다른 호출이라면 두 호출이 모두 성공한 동일 검증 cycle만 `VALID`로 인정한다. 일부 성공은 정상 전체잔고로 간주하지 않는다.

### 7-6. 캐시 즉시 사용 조건

개념상 다음을 모두 만족해야 한다.

```python
cache.status == "VALID"
and cache.stock_code == position.stock_code
and cache.position_version == position.position_version
and cache.age_sec <= 45
and cache.account_qty >= position.auto_managed_qty
and cache.sellable_qty >= position.auto_managed_qty
and cache.pending_sell_qty == 0
and not cache.external_order_detected
and position.status == "OPEN"
and not position.exit_order_in_progress
```

조건 하나라도 불만족이면 캐시 즉시매도를 사용하지 않고 안전조회 경로로 전환한다.

### 7-7. 즉시 무효화 사건

- 자동매수·자동매도 주문 접수
- 자동매수·자동매도 체결 및 부분체결
- 취소·정정·거부·응답불명확
- 수동 또는 외부 주문 감지
- 계좌 보유수량·매도가능수량 변경
- 포지션 상태나 `position_version` 변경
- 프로그램 재시작, WebSocket 재연결
- 응답 종목·수량 불일치 또는 파싱 오류
- 이전 요청의 늦은 응답이 최신 cache generation을 덮으려는 경우

특히 실제 주문 제출 상태를 원자적으로 고정하면서 캐시를 먼저 무효화해 같은 캐시를 이용한 중복매도를 막는다.

## 8. 캐시·안전조회 실패 정책

1. 갱신 실패 시 기존 캐시가 45초 이내이고 그 뒤 상태변경이 없으면 계속 사용할 수 있다.

3. 안전조회 실패·시간초과 시 오래된 정보로 무조건 매도하지 않는다.

6. 주문 접수 응답이 불명확하면 즉시 재주문하지 않고 미체결 조회로 접수 여부부터 확인한다.
7. 매도 거부 시 `EXIT_ERROR`로 전환하고 자동 반복매도를 차단하며 종목명·코드·수량·오류원인을 알린다.

## 9. 확정 주문 상태·경합 처리

### 9-1. 중복과 우선순위

- 같은 종목의 최초 확정 청산사유 하나만 유지한다.
- TP/SL tick이 반복돼도 중복 주문하지 않는다.
- 동시에 여러 종목이면 STOP_LOSS 우선, 그 다음 TAKE_PROFIT, 동일 등급은 trigger 시각 순서다.
- 신규매수와 연구는 실제 청산보다 항상 뒤다.

### 9-2. 부분체결

- 체결수량은 부모의 `requested_qty - unfilled_qty` delta invariant를 유지한다.
- 체결된 수량과 잔량을 분리한다.
- 전량 체결 전까지 포지션을 종료 처리하지 않는다.
- 잔량은 동일 청산사유로 계속 관리한다.
- 재주문 전 기존 주문의 접수·미체결·취소 여부를 확인한다.

### 9-3. 수동·외부 주문

- 감지 즉시 해당 cache와 position generation을 무효화한다.
- `external_qty`와 `auto_managed_qty`를 섞지 않는다.
- 계좌 재동기화 전 해당 종목의 신규 자동주문을 차단한다.

### 9-4. 재시작·연결끊김·종료

- 프로그램 재시작 시 저장상태, broker 보유, 매도가능수량, 미체결을 대조하기 전 신규매수를 금지한다.
- WebSocket 재연결 시 cache를 무효화하고 보유종목을 재검증한다.
- 09:30 이후에는 신규 실매수만 막고 기존 포지션 TP/SL과 15:20 청산 관리는 계속한다.
- 종료 시 보유종목과 미체결 주문을 명확히 경고하고 material state를 동기 저장한다.

## 10. 검토 후 채택하지 않은 청산안

### 10-1. +2.0%에서 +2.5% 익절 지정가 선주문

장점:

- 목표가 도달 감지와 사전조회 지연을 피할 수 있다.
- 미리 주문 대기해 두산퓨얼셀·현대약품 같은 목표가 접촉 후 하락 사례의 익절 slippage를 줄일 가능성이 있다.

기각 사유:

- 해당 수량이 익절 주문에 묶여 손절 시 기존 주문 취소확인이 필요하다.
- 취소 접수→취소 확인→매도가능수량 복구→손절 주문 과정이 추가된다.
- +2.0%에서 -1.0%까지 3.0%p 급락한 뒤 취소를 시작하면 손절선을 통과할 수 있다.
- 가격 왕복 시 주문·취소 반복, 부분체결, 주문번호 추적, 중복·초과매도 위험이 커진다.
- 일반 국내주식 API에서 신뢰할 수 있는 broker OCO/bracket을 확인하지 못했다.
- 과거 수량·초과매도 사고를 고려할 때 사용자의 손실회피 성향과 맞지 않는다.

따라서 v1.7.1은 **접근 시 주문이 아니라 캐시만 준비하고, 실제 TP/SL에서 시장가 청산**한다. 목표가 선주문, TP/SL 주문 반복 전환, 공격적 지정가는 적용하지 않는다. 향후 OCO 지원 또는 취소·정정 실측이 확보될 때만 별도 재검토한다.

### 10-2. 5초 고정 계좌조회

조회 자체가 5~7초 걸렸으므로 고정 5초 반복은 중첩·API 점유·전체 지연을 유발할 수 있어 기각한다. 단일 coalescing 갱신과 적응형 30초/근접 우선갱신을 사용한다.

### 11-2. 필수 수정

- 연구 계산 자체를 live WebSocket 경로에서 완전히 분리한다.
- WS callback은 실제 가격 cache, 실제 청산 판단·제출 후 연구 snapshot을 nonblocking queue로 넘긴다.
- P1 queue의 `put(timeout=5)`가 WS 스레드를 최대 5초 막지 않게 한다.
- queue 포화 시 P1 최종결과를 조용히 폐기하지 않는다. 별도 복구 spool/저우선 writer를 사용하되 WS를 막지 않는다.
- P2 상세 snapshot은 명시적으로 coalesce/degrade할 수 있으며 감소량과 사유를 기록한다.
- 연구 executor/writer, 신규매수, cache refresher, 실제 exit executor를 공유하지 않는다.
- 실제 청산 제출 전에 연구 CSV I/O가 없어야 한다.

### 11-3. `save_live_state()` 과다 호출

`update_live_position_on_price()`는 상태변경이 없는 일반 tick에서도 `save_live_state()`를 호출한다. 이는 실제 live-check 최대 2.6초 spike의 유력 원인이다.

필수 수정:

- 매 tick 동기 저장을 제거한다.
- `last_price` 같은 고빈도 값은 dirty/coalesced 비동기 저장한다.
- 체결, 주문접수, trigger 고정, 상태전환, 수량변경, 종료처럼 material event는 즉시 원자 저장한다.
- 기존 atomic temp/replace와 재시작 복구 안전성은 유지한다.

- 실제 계좌변동 없이 설정·파일초기화·종료 정상
- release 기본 `AUTO_TRADE_ENABLED=False`

### 16-3. 신규 Shadow 오류

- 결측 history 전 조합에서 TypeError 0건
- 연구 예외가 main scan을 중단하지 않음
- 299회 오류 재현 입력을 replay해 정상 통과

### 16-4. 캐시·청산

- +2.0/-1.0 접근 시 최초 조회 요청
- 0.2~0.5%p 구간 30초 갱신과 중복 coalescing
- 0.2%p 근접 시 10초 초과 cache 우선갱신
- 실제 TP/SL에서 갱신 완료를 기다리지 않음
- 45초 이내 유효 cache면 추가 broker 조회 없이 주문 API 호출
- cache 만료·version mismatch·pending sell·외부주문이면 fallback
- 오래된 응답이 최신 generation을 덮지 못함
- 주문 제출 즉시 cache invalidation과 중복 SELL 차단
- 사용자 TP/SL 변경 시 접근 기준 자동 계산

성능 초기 합격 목표:

```text
유효 cache 경로 trigger→exit worker submit: 0.2초 이내
유효 cache 경로 trigger→매도 API 호출 시작: 0.5초 이내
신규매수 precheck 또는 연구 때문에 실제 exit가 대기한 건수: 0
```

broker 주문 API 자체 응답시간과 프로그램 내부 지연을 분리해 기록한다. 위 숫자는 실환경 관찰로 재조정할 수 있지만 단계 누락은 허용하지 않는다.

### 16-5. 주문 안전 회귀

- partial fill delta와 requested_qty 초과 invariant
- broker held/sellable/pending 불일치
- 외부/수동수량 분리
- 중복 BUY/SELL 차단
- ORDER_STATUS_UNKNOWN SAFE HALT
- EXIT_ERROR와 반복매도 차단
- 응답불명확 후 조회 없이 재주문 금지
- 재시작 reconcile 전 신규매수 금지
- shutdown 후 신규주문 차단
- atomic live_state 복구

### 16-6. 연구과부하

- 감시종목 50개, WIDE 500 episode, 169-grid, 다수 동시 tick과 청산을 replay
- 연구 queue backlog와 writer 실패 중 SL trigger 주입
- 실제 청산 판단과 worker 제출 전에 연구 계산/I/O 없음
- WS 경로에서 blocking queue put 없음
- P1 보존, P2 degrade 기록
- 연구가 exit executor·cache refresher·order dispatcher lock을 점유하지 않음

### 16-7. 메시지·CSV

- 사용자 설정을 여러 값으로 바꿔 Telegram TP/SL·목표가·손절가 일치
- 복구 포지션도 entry-time snapshot 표시
- policy Shadow 파일 실제 생성
- system CSV invalid UTF-8·고아행·중복 header 없음
- live trades/performance 역할 중복 해소
- cache/latency 필수 컬럼 완전성

## 19. 최종 인수인계 요약

> 2026-09-07의 실제 T250/S150 trigger는 정상 작동했지만 Telegram은 +2.00%로 하드코딩돼 잘못 표시됐다. 네 거래의 주된 문제는 TP/SL 계산이 아니라 trigger 후 broker 안전조회·주문 API와 공용 lock 때문에 주문 제출까지 9.5~12.65초 지연된 것이다.

> v1.7.1은 안전검사를 제거하지 않고 TP/SL 0.5%p 전부터 broker 계좌상태를 비동기 사전검증한다. 0.2~0.5%p 구간은 완료 후 30초 갱신, 0.2%p 이내에서는 10초보다 오래된 cache를 우선 갱신하며, 실제 기준가에서는 45초 이내의 상태변경 없는 유효 cache로 추가 조회 없이 즉시 시장가 청산한다.

> 실제 exit는 cache refresh, 신규매수, 연구보다 우선한다. 신규매수 precheck와 exit의 공용 lock 경합을 제거하고, exit 전용 executor 또는 우선순위 dispatcher를 둔다. 손절은 익절보다 우선하며 중복·부분체결·응답불명확·수동주문·재시작 안전장치를 유지한다.

> 연구 계산과 CSV 저장은 WebSocket 실제매매 경로에서 완전히 분리한다. P1 queue의 5초 blocking과 매 tick `save_live_state()`를 제거하되, material event는 즉시 원자 저장한다.

> 신규 Shadow 결측값의 문자열/숫자 비교 오류, policy Shadow의 `BASE`/`FIRST_75_PASS` 식별 오류, CSV 동시쓰기·중복 파일 문제를 수정한다. 2026-09-07은 약 24% 스캔 오류가 있는 부분수집일이며 하루 결과만으로 T250/S150을 변경하지 않는다.

> 목표가 지정매도 선주문, 공격적 지정가, TP/SL 주문 반복 전환, 5초 고정조회는 채택하지 않는다. 사용자는 종목 수·금액·총예산·시간·전략·TP/SL을 바꿀 수 있고, 테스트와 숨은 하드코딩이 권고 기본값을 강제하면 안 된다.

이 여섯 문장이 v1.7.1 전체 코드 작성의 최상위 기준이다.
