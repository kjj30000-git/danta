## 4. P0-1 — 유효 cache 자기거부 오류

### 4-1. 확인된 원인

현재 흐름은 다음과 같다.

1. `submit_live_exit()`가 최초 TP/SL trigger를 원자적으로 고정한다.
2. 같은 함수가 중복청산 차단 목적으로 `exit_order_in_progress=True`를 설정한다.
3. exit worker가 `_cache_snapshot_for_exit()`를 호출한다.
4. cache 검사기가 `exit_order_in_progress=True`를 `EXIT_IN_PROGRESS`로 거부한다.

따라서 현재 청산 작업 자신이 세운 정상 상태 때문에 cache를 사용할 수 없다.

실측 근거:

- 필옵틱스: cache age 4.864초, miss `EXIT_IN_PROGRESS`
- 주성엔지니어링: cache age 17.853초, miss `EXIT_IN_PROGRESS`
- 두 건 모두 45초 이내였지만 fallback 조회로 전환됐다.
- 우리기술 cache age 58.788초는 `STALE`이므로 fallback이 정상이다.
- 스카이랩스는 stale·수량·version 불일치가 있어 fallback이 정상이다.

### 4-2. 필수 수정 원칙

- `exit_order_in_progress` 검사를 단순 삭제하지 않는다.
- 현재 확정된 청산 작업이 소유한 상태와, 그 전에 존재한 다른 SELL/청산 작업을 구분한다.
- 권장 방식은 trigger마다 불변 `exit_attempt_id` 또는 generation/token을 발급하는 것이다.
- `submit_live_exit()`가 token을 원자적으로 저장하고 exit queue/worker에 같은 token을 전달한다.
- cache 검사 시 `position.exit_attempt_id == worker.exit_attempt_id`이면 현재 작업으로 인정한다.
- token이 다르거나 기존 SELL 주문·제출 intent·미체결이 있으면 중복으로 차단한다.
- 실제 SELL 제출 직전에 token과 position 상태를 다시 확인한다.
- 주문 제출과 동시에 cache를 무효화하는 부모 안전장치는 유지한다.
- 현재 작업이 실패하면 `EXIT_ERROR`/차단 상태와 token 정리 정책을 명확히 한다.

### 4-3. 캐시 즉시청산 합격 조건

다음을 모두 만족한 동일 종목의 현재 exit attempt만 cache를 사용할 수 있다.

```text
cache VALID
cache age <= 45초
cache generation 최신
position_version 일치
broker held/sellable >= auto_managed_qty
broker pending sell 없음
external order 없음
현재 worker token == position exit_attempt_id
기존 중복 SELL/order submit intent 없음
```

필옵틱스·주성엔지니어링 조건을 재현한 시험에서는 추가 broker 조회 없이 SELL API로 진행해야 한다.
우리기술·스카이랩스 조건을 재현한 시험에서는 안전하게 fallback해야 한다.

## 5. P0-2 — 연구부하와 경고 폭증

### 5-1. 관측

2026-09-08 장중 업로드 시점 파일 크기:

```text
scanner_system_v171.csv       약 73 MB
research_performance_v171.csv 약 11 MB
```

사용자 화면에는 Telegram이 아닌 연구부하 메시지가 반복 출력됐다.

현재 위험:

- `research_tick_queue` 포화 시 연구 snapshot이 감소한다.
- queue full 경고를 tick마다 동기 `log()`하면 화면 출력과 `scanner_system` CSV 쓰기가 WebSocket 호출경로에서 반복된다.
- 경고 기록이 다시 I/O 부하와 대용량 system 파일을 만든다.
- P1 queue overflow 복구가 계속 점유 중인 단일 `RESEARCH_COMPUTE_EXECUTOR`에 제출되면 복구 작업이 실행되지 못하고 대기할 수 있다.
- 연구부하는 오늘 13~18초 청산 지연의 직접 원인은 아니었지만, 실시간 tick 수신과 데이터 완전성에 별도 위험이다.

### 5-2. 반드시 수정할 최소 범위

1. **queue-full 경고 rate limit/coalescing**
   - 매 tick 동기 로그 금지
   - 최초 1회 후 최소 30~60초 간격 요약 로그
   - 요약에는 기간 중 drop/coalesce 수와 queue 최대치 기록

2. **WS callback의 파일 I/O 제거**
   - compute queue 포화 시 counter만 원자 증가
   - system CSV 기록은 별도 저우선 worker가 수행
   - 실제 청산 판단·worker 제출 전에 연구 계산·연구 CSV·경고 CSV I/O가 없어야 한다.

3. **P1 복구 실행경로 분리**
   - 무한 실행 중인 research compute worker와 같은 단일 executor에 spool 작업을 제출하지 않는다.
   - 별도 bounded recovery queue/writer 또는 전용 단일 worker를 사용한다.
   - P1 최종결과는 보존하고, overflow 발생·복구 성공·실패를 집계한다.

4. **P2 최신값 coalescing/degrade**
   - 동일 종목의 처리 전 tick이 여러 개 쌓이면 최신 tick 중심으로 합칠 수 있다.
   - 감소량과 사유를 집계하되 매 tick 로그하지 않는다.
   - 기존 P2 연구 종류와 CSV schema는 변경하지 않는다.

5. **성능기록량 제한**
   - `WS_TICK_1S_AGG`를 모든 종목 매초 무조건 저장하지 않도록 집계 간격을 늘리거나 과부하 시 표본화한다.
   - 정상상태와 과부하상태의 기록정책을 구분한다.
   - 단, 청산·cache·broker call latency 기록은 축소하지 않는다.

### 5-3. 기본 권장값

새로운 사용자 전략설정으로 만들지 말고 내부 안전 기본값으로 둔다.

- 주문 제출 시 cache 즉시 무효화

- shutdown 시 bounded flush 후 남은 항목 수를 기록하고 무한 대기하지 않음

### 7-4. 비실주문 cold-start
