# 4. v1.6.8 주문엔진 평가 — 현재 정상동작 부분은 보존

## 4-1. 주문/체결수량

오늘 실제 주문은 모두 요청수량과 broker 누적체결수량이 정확히 일치했다.

```text
흥구석유 BUY  82 / 82
흥구석유 SELL 82 / 82
일동제약 BUY  57 / 57
일동제약 SELL 57 / 57
```

금호전기에서 과거 발생했던 과다 누적체결 인식 유형의 문제는 재발하지 않았다.

따라서 아래 구조는 변경하지 않는다.

```text
broker_filled_qty = requested_qty - unfilled_qty
delta_qty = broker_filled_qty - previous_broker_filled_qty
```

# 10. 신규 연구 1 — WIDE_HIGH_GAP_SHADOW

## 목적

현재 전체 scanner의 넓은 고점이격 상한:

```python
MAX_HIGH_GAP = 3.0
```

현재 `LIVE_MAX_HIGH_GAP = 1.5`는 **LIVE_FILTER_SHADOW 연구용**이며 실제 FIRST_75_PASS 주문필터가 아니다.

따라서 단순히 `LIVE_MAX_HIGH_GAP 1.5 → 더 큰 값`으로 바꾼다고 FIRST_75_PASS 실제 횟수가 늘어나는 구조가 아니다.

또한 `MAX_HIGH_GAP`은 점수체계 자체의 high-position 상대구간 계산에도 사용되므로,
기존 값을 바로 4~5%로 변경하면 **후보범위와 점수체계가 동시에 변해 원인분석이 어려워진다.**

### 합의

기존 `MAX_HIGH_GAP = 3.0` 및 기존 점수체계는 유지한다.

대신 별도 연구군:

```text
WIDE_HIGH_GAP_SHADOW
```

를 추가한다.

### 1차 연구범위

```text
high_gap > 3.0%
high_gap <= 4.5%
```

### 중요 구현 원칙

현재 scanner가 `high_gap > MAX_HIGH_GAP`에서 FILTER_EXIT하기 때문에,
이 연구군은 **FILTER_EXIT 직전 또는 별도 Shadow capture path에서 기록**해야 한다.

기존 scanner/score/FIRST_75_PASS 조건을 변경해서 구현하지 않는다.

### 기록/추적

가능한 기존 연구체계와 같은 형식으로:

```text
stock_code / stock_name
time / session
score 및 score_detail
high_gap
high_gap_change_60s
price_change_15s/30s/60s/120s/180s/300s
history_available_sec
trading_value / volume / growth metrics
WATCH Episode id
MFE / MAE
169 TP/SL grid
ENTRY_PATH
POST_EXIT (가능한 범위)
```

을 추적한다.
