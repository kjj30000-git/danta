## 3. 근본 원인

### 3.1 주문과 조회가 동일한 공용 rate-limit 관문을 사용

부모 코드의 `kiwoom_post()`는 주문·잔고·종목조회 모두 `wait_api_rate_limit()`을 호출한다. `API_RATE_LOCK`은 전체 REST 요청의 최소 간격을 지키지만 요청 우선순위를 구분하지 않는다.

동시에 8개 scanner worker가 `KA10001` 조회를 수행하면 여러 조회가 공용 lock 앞에 대기한다. 그 뒤 손절·익절·매수 주문이 들어와도 이미 대기 중인 조회보다 먼저 처리된다는 보장이 없다. 실시간 WebSocket은 가격을 제때 감지했고 exit worker 투입도 사실상 즉시였지만, 실제 주문이 공용 관문에서 기다렸다.

### 3.2 현재 지표가 대기와 통신을 합쳐 기록

현재 `order_api_duration_ms`에는 API 슬롯 대기와 실제 HTTP 왕복시간이 함께 들어간다. 어느 구간이 지연됐는지 운영 중 즉시 구분할 수 없다.

### 3.3 장기 미체결 BUY 통제가 없음

원익 BUY는 접수 뒤 약 134초 후 체결됐다. 오래된 진입 신호가 뒤늦게 체결되면 진입가·시장상태가 달라져 전략 의미가 약해진다. 접수 후 일정 시간 내 체결되지 않은 잔량을 취소하는 일반 정책이 필요하다.

### 3.4 watchdog이 정상적인 진행 상태를 구분하지 못함

worker가 `WAITING_API_SLOT`, `API_SUBMITTING`, `WAITING_FILL` 중이어도 단순 heartbeat 기준으로 비정상 판정할 수 있다. 주문 처리 중 dispatcher 재시작이나 SAFE HALT가 발생하면 신규매수가 불필요하게 중단되고, 잘못 구현하면 중복주문 위험도 생긴다.

## 4. v1.7.1.3 구현 범위

### 4.1 우선순위 API admission controller

기존 `API_RATE_LOCK`의 단순 경쟁을 주문 우선순위를 인식하는 단일 admission controller로 교체한다.

| 우선순위 | 요청 종류 | 예시 |
|---:|---|---|
| P0 | 손절 및 즉시 위험축소 | SL SELL, 청산 전 필수 잔량 취소 |
| P1 | 기타 청산 | TP SELL, 시간청산, 수동 긴급청산 |
| P2 | 취소·정정 | 미체결 BUY 잔량 취소, 위험을 줄이는 정정 |
| P3 | 신규 BUY | 조건 통과 실제 진입 |
| P4 | 주문 관련 확인 | 미체결·체결·보유수량 reconciliation |
| P5 | scanner 조회 | `KA10001` 등 종목조회 |
| P6 | 기타 REST | 비긴급 연구·부가조회 |

구현 요구사항:

- `Condition`과 우선순위 waiter 또는 동등한 명시적 구조를 사용한다.
- 같은 우선순위에서는 요청 등록 순서를 보존한다.
- 모든 요청은 기존 전역 최소 호출간격을 준수한다.
- 주문이라고 별도 lock으로 우회해 호출제한을 깨면 안 된다.
- 이미 HTTP 전송을 시작한 요청은 취소하지 않는다.
- 아직 admission을 받지 않은 낮은 우선순위 요청만 대기시킨다.
- 주문 대기자가 생기면 새 scanner 요청은 주문이 슬롯을 얻을 때까지 앞서지 못한다.
- 예외·timeout에도 admission 상태와 waiter가 반드시 정리돼 deadlock이 없어야 한다.
- starvation 방지를 위해 장시간 대기 로그를 남기되, 주문보다 scanner를 먼저 보내는 강제 승격은 하지 않는다.

성능 목표는 synthetic 부하에서 “8개 scanner waiter 뒤에 들어온 주문의 API 슬롯 획득 대기”를 통상 0.35초 이내로 만드는 것이다. 이는 broker 응답·시장 체결시간까지 0.35초를 보장한다는 뜻이 아니다.

### 4.2 API 호출 초과 격리

2026-09-10 `KA10001` 429는 3회(09:23:16, 11:51:51, 18:35:17), 동일 오류흐름은 각 5회였다. 주문 429는 확인되지 않았다. 또한 `KA10001` 연결 timeout이 3회 있었다.

- `KA10001`에는 요청 ID별 최소 간격 0.30초를 적용한다.
- 429가 발생하면 해당 조회 종류만 backoff한다.
- 같은 scan에서 즉시 반복 재시도하지 말고 다음 scan으로 넘긴다.
- 429 backoff가 주문 admission을 막지 않아야 한다.
- 전체 API 간격을 무작정 늘려 주문까지 느리게 하지 않는다.
- API ID, request class, priority, slot wait, HTTP duration, status, backoff를 기록한다.

### 4.3 BUY 접수 후 5초 미체결 관리

기본값 `LIVE_BUY_FILL_TIMEOUT_SEC = 5.0`을 첫 셀에 노출한다. 타이머 기준은 신호시각이 아니라 broker 주문접수시각이다.

| 5초 시점 상태 | 처리 |
|---|---|
| 체결 0주 | 미체결 전량 취소 → 취소 확인 → 해당 종목 당일 재진입 차단 |
| 일부 체결 | 잔량 취소 → 실제 체결수량·평균가로 포지션 생성 → 정상 TP/SL 관리 |
| 이미 전량 체결 | 취소하지 않고 전체 포지션 정상 관리 |
| 취소와 최종체결 경합 | broker 체결이 최종 진실. 실제 체결수량을 관리 |
| 취소 응답 timeout/접수 불명 | `ORDER_STATUS_UNKNOWN`, 중복 취소·신규주문 금지, 신규매수 HALT 후 broker 대조 |

- 기존 `submit_cancel_order`와 주문원장을 재사용하되, 수량·중복방지 invariant를 유지한다.
- 취소거부가 “이미 전량체결”로 명확하면 오류로 재주문하지 말고 포지션 관리로 전환한다.
- 원익 사례만으로 새 VI 진입필터를 추가하지 않는다. 가능하면 당시 VI·세션상태를 로그 필드로 수집한다.

### 4.4 dispatcher watchdog 상태 모델 수정

worker/dispatcher 상태를 최소 다음으로 명시한다.

`IDLE`, `VALIDATING`, `WAITING_API_SLOT`, `API_SUBMITTING`, `WAITING_FILL`, `RECONCILING`, `FAILED`

- `WAITING_API_SLOT`은 admission controller 등록시각과 함께 정상 진행으로 본다.
- `API_SUBMITTING`은 HTTP timeout과 작은 여유시간 전까지 정상으로 본다.
- `WAITING_FILL`은 주문접수와 주문번호가 있으면 정상 추적 상태다.
- future가 예기치 않게 종료됐거나 `IDLE` heartbeat가 임계값을 넘을 때만 dispatcher 불건전으로 판정한다.
- API timeout 이후에는 `ORDER_STATUS_UNKNOWN`으로 전환하고 신규매수를 HALT한 뒤 broker 상태를 대조한다.
- 진행 중 주문을 watchdog이 자동 재제출하거나 동일 worker를 중복 실행하면 안 된다.

### 4.5 단계별 timestamp와 duration

표시용 시각은 timezone-aware `datetime`, 구간 측정은 시스템 시각 보정의 영향을 받지 않는 `time.monotonic()`을 사용한다.

BUY 필수 시각:

- `signal_time`
- `precheck_started_at`, `precheck_finished_at`
- `api_slot_requested_at`, `api_slot_acquired_at`
- `api_started_at`, `order_accepted_at`
- `first_fill_at`, `final_fill_at`

SELL 필수 시각:

- `trigger_time`
- `api_slot_requested_at`, `api_slot_acquired_at`
- `api_started_at`, `order_accepted_at`
- `first_fill_at`, `final_fill_at`

파생 지표:

- API slot 대기시간
- HTTP 왕복시간
- 신호/트리거→주문접수
- 주문접수→최초체결
- 주문접수→최종체결
- 신호/트리거→최종체결 총 소요시간
- trigger 대비 및 목표/손절 기준 대비 slippage

기존 `order_api_duration_ms`는 하위호환을 위해 유지하되, `api_slot_wait_ms`와 `http_duration_ms`를 반드시 추가한다.

- `live_state` atomic save·복구
- 연구그룹, watch episode, post-exit, 169개 TP/SL grid와 기존 출력파일
- v1.7.1.2의 주문 후 안전장치 및 종료 후 주문차단

이번 버전에서 전략필터, 점수, 투자금, 최대종목수, TP/SL, 진입시간을 임의 변경하지 않는다.

## 7. 이번 버전에서 하지 않을 것

- Kiwoom 서버 stop/자동감시 주문을 실전에 바로 연결하지 않는다. 주문유형 지원범위, 수량예약, TP와의 OCO, 미체결 위험을 소액 독립시험한 뒤 별도 버전에서 판단한다.
- 원익 지연을 VI로 단정하거나 VI 필터를 추가하지 않는다.
- 안전검사를 제거해 속도를 만드는 변경을 하지 않는다.
- 전송 중 HTTP를 강제 종료하지 않는다.
- 주문용 별도 rate-limit lock으로 우회해 증권사 호출 제한을 위반하지 않는다.
- `requests.Session` 교체 등 근거 없는 광범위 리팩터링을 하지 않는다.

## 8. 필수 회귀시험

1. 부모 정의·셀·상수·함수·출력파일 보존 비교
2. 전체 셀 compile, import·미정의 name 검사
3. 외부 연결을 막은 cold-start
4. 8개 scanner waiter 뒤 SL이 다음 API 슬롯 획득
5. 동시 SL·TP·BUY·조회에서 확정 우선순위와 동일순위 FIFO 확인
6. 우선처리 중에도 전역 최소 호출간격 위반 없음
7. `KA10001` 429가 해당 조회만 backoff하고 주문은 진행
8. BUY 5초 0체결 → 전량취소 → 당일 재진입 차단
9. BUY 부분체결 → 잔량취소 → 실제 체결수량 포지션 관리
10. 취소와 최종체결 경합 → 중복주문 없이 broker 체결수량 반영
11. 취소 응답 불명 → `ORDER_STATUS_UNKNOWN`, 무재시도, 신규매수 HALT, 상태대조
12. `WAITING_API_SLOT`/`API_SUBMITTING` 중 watchdog false halt 없음
13. worker 실제 종료·heartbeat 정지에는 정확히 HALT
14. SELL timeout/무응답 시 submit intent 보존 및 중복매도 없음
15. FAST_CACHE_EXIT와 SAFE_REST_EXIT 각각 end-to-end 성공
16. 외부 주문·수동 보유수량·부분체결·초과수량 invariant 회귀
17. 알림과 CSV의 timestamp·duration 산식 일치
18. Telegram 실패가 주문 latency/state에 영향 없음

mock 테스트 로그와 검증표가 없으면 실전 release 승인으로 간주하지 않는다.

## 9. 승인 기준과 배포 권고

- synthetic scanner 부하에서 긴급 주문의 API slot wait가 통상 350ms 이내
- 주문 우선처리에도 호출간격·중복방지·수량 안전장치 위반 0건
- watchdog false halt 0건
- 5초 BUY 미체결·부분체결·취소경합 시나리오 전부 통과
- trigger/signal, 주문접수, 최초/최종체결, 각 구간 및 총 소요시간이 로그·CSV·Telegram에 일치
- 주문 응답 불명 상태에서 자동 재주문 0건

첫 실전 전에는 `AUTO_TRADE_ENABLED=False`로 mock·cold-start·회귀시험을 완료한다. 이후 자동매매는 소액 1건으로 주문 우선권, 미체결 취소, watchdog, 알림시간을 먼저 확인한 뒤 확대한다. “가격을 찍는 즉시 체결”은 시장 유동성과 broker 응답 때문에 보장할 수 없지만, 내부 조회 대기로 주문 제출이 늦어지는 구조는 제거해야 한다.
